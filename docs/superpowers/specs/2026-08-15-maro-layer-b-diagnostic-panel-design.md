# Maro Layer B-1 — 진단 패널과 해법 적용 설계

작성일: 2026-08-15
선행: Layer A (`boad`/`onfix`/`book`) 완료 — `docs/superpowers/specs/2026-08-14-maro-troubleshooting-ecosystem-design.md` §4.2, §4.3

## 1. 목적

Layer A는 원인 정보를 **모으고 쌓는** 데까지 왔다. 사용자가 그걸 볼 방법은 아직 스크립트 에디터 한 줄뿐이고, 등록된 해법을 다시 꺼내 쓸 방법은 없다.

Layer B-1은 그 절반을 채운다.

1. **좁힌다** — 진단이 시각과 함께 보이고, 같은 실패의 반복은 한 줄로 접혀 그 아래 깔린 다른 실패가 드러난다. 열 개가 한 틱에 몰아쳤는지 몇 분에 걸쳐 벌어졌는지가 보인다
2. **본다** — 하나를 고르면 `onfix`가 포착한 원인 컨텍스트가 펼쳐지고, 포착하지 못한 자리는 빈칸이 아니라 못 채운 이유가 나온다
3. **안다** — `book`에 있는 실패면 "전에 본 문제"로 표시되고 과거 분석이 함께 나온다
4. **고친다** — 해법이 기계가 실행할 수 있는 형태로 기록돼 있으면 버튼 하나로 적용되고, `Ctrl+Z`로 되돌아간다
5. **잃지 않는다** — Maya가 죽어도 그 직전의 진단이 저널에 남고, 다음 실행이 비정상 종료를 알아채 그것을 되살린다

이 서브시스템은 플러그인의 **보조 유틸리티**다. 본체 동작에 부담을 주지 않는 것이 기능을 늘리는 것보다 우선한다.

**단, 그 절약은 원인 보고에서 하지 않는다.** 가벼워지는 대가는 UI의 표현력에서 치른다. 무엇을 보여줄지에서 치르지 않는다.

## 2. 범위

### 포함 (B-1)

- 진단 패널 — `workspaceControl` 안의 Maya 네이티브 UI
- 프레젠터 — 화면에 나갈 행·상세·버튼 상태를 계산하는 순수 C++ 층
- 상시 메인 스레드 작업 큐
- 구조화된 해법 동작 3종과 그 적용 경로 (undo 포함)
- `book` 스키마에 `remedyAction` 추가
- **`DiagRecord`에 발생 시각과 순번 추가** — Layer A 변경. 근거는 §3.4
- **크래시를 건너 살아남는 저널**과 비정상 종료 감지 — §3.6

### 경량화하면서도 양보하지 않은 것

이 서브시스템은 보조 유틸리티이지만, **원인 보고 자체는 깎지 않는다.** 가벼워지는 대가는 UI의 화려함에서 치르고 정보에서 치르지 않는다.

Qt를 빼면서 잃은 것은 행별 색상 같은 표현력이지 정보가 아니다. 심각도·시각·기지 여부·반복 횟수·원인 컨텍스트·과거 분석·해법은 네이티브 위젯에서도 전부 나온다.

반대로 원인 보고를 위해서라면 Layer A를 건드리는 것도 감수한다 — 시각과 순번이 그 경우다.

### 제외 — Layer B-2

- Qt 위젯판 패널
- 첫 로드 시 두 판 중 하나를 고르게 하는 안내와 그 선택의 저장

B-2가 싸게 붙으려면 B-1이 지켜야 할 것이 있다. §7에 적는다.

### 제외 — Layer C

감시자 프로세스, `offix`, `ghost`, `OSbridge`, 정본 `book` 쓰기. Layer A와 마찬가지로 B-1은 **감시자가 영원히 없다고 가정하고** 동작한다.

### 제외 — 명시적으로 안 하는 것

- **자동 적용.** 사용자가 버튼을 눌러야 적용된다. 이 결정은 Layer A 설계 때 한 번 뒤집혔다가 확정됐다
- **동작 3종 외 추가.** 아래 §4.2의 근거를 넘는 동작은 실제 필요가 생긴 뒤에 넣는다
- **Layer A의 무한 스트림 자체를 고치는 것.** 패널이 그리는 양만 제한한다 (§5)

## 3. 아키텍처

### 3.1 단위 경계

Maya를 아는 코드와 판단하는 코드를 나눈다. 그래야 판단이 gtest로 덮이고, Maya가 필요한 부분만 수동 확인으로 남는다.

| 단위 | 의존성 | 책임 |
|---|---|---|
| 프레젠터 (`src/maro_diag/`) | 없음 | 레코드 스냅샷 + book 항목 → 행·상세·**적용 버튼 활성 여부** |
| 패널 UI (Python) | Maya UI 커맨드 | 프레젠터 결과를 위젯에 얹고 클릭을 커맨드로 넘김 |
| 플러그인 글루 (`src/maro_plugin/`) | Maya | 스냅샷 채취, 커맨드, 상시 큐 |

프레젠터를 새 라이브러리로 만들지 않고 기존 `maro_diag`에 넣는다. `maro_diag`는 이미 Maya에 의존하지 않고 자체 gtest 바이너리를 갖고 있다 — 새 타깃도, 새 테스트 바이너리도 필요 없다.

### 3.2 뷰가 알 필요 없는 것

프레젠터의 출력 `PanelView`와 입력 `ApplyIntent`(행 번호 하나)는 **어떤 UI 기술도 전제하지 않는다.** Maya 위젯인지 Qt 위젯인지는 프레젠터가 모른다.

이것이 B-2를 싸게 만드는 지점이다. Qt판이 붙을 때 판단 로직은 한 줄도 다시 쓰지 않는다.

### 3.3 스냅샷은 살아있는 씬을 조회하지 않는다

"적용 버튼을 켤 수 있나"는 대상 노드가 아직 존재하는지에 달렸고, 그건 Maya 질의다. 프레젠터는 순수해야 하므로 **스냅샷을 뜨는 메인 스레드 시점에 그 사실까지 해결해서** 담는다. 프레젠터는 받은 사실만 쓴다.

Layer A의 "패널은 자체 상태를 갖지 않는다"와 같은 규율이다. 패널은 `boad`의 인메모리 스트림과 `book` 파일만이 진실이라고 본다.

### 3.4 갱신 주기

매 틱 스냅샷을 다시 만들지 않는다. `BoadMaro::recordCount()`만 읽고(뮤텍스 한 번) 지난번과 다를 때만 다시 만든다. 레코드는 제거되지 않으므로 이 값은 단조 증가한다 — 줄어들었다면 `resetForTest()`가 불린 것이므로 그때도 다시 만든다.

**행 목록을 그리는 데 `book` 조회는 필요 없다.** `DiagRecord`는 `servedFromBook`·`remedy`·`priorAnalysis`를 발생 시점에 이미 담고 있다. 기지 여부는 레코드 자체에서 공짜로 나온다.

선택했을 때만 `book`을 다시 보는 이유는 I/O를 아끼려는 것이 아니라 **레코드가 남은 뒤에 등록된 해법**을 반영하기 위해서다. 사용자가 스스로 고치고 해법을 등록하면, 이미 목록에 있는 그 에러도 이제 해법을 갖는다.

프레젠터의 진입점은 둘이다.

| 진입점 | 입력 | 출력 |
|---|---|---|
| 행 목록 | 레코드 스냅샷 | 시각, 심각도, 기지 여부, 반복 횟수, 한 줄 요약 |
| 상세 | 레코드 하나 + 그 해시의 현재 book 항목 + 대상 노드 존재 여부 | 원인 컨텍스트, 과거 분석, 해법 설명, 적용 가능 여부와 그 이유 |

**`DiagRecord`에 시각과 순번을 추가한다.** 지금은 둘 다 없어서 순서 말고는 아무것도 답할 수 없다. 원인을 좁히는 질문은 대개 시간에 걸려 있다 — 재생을 누르기 전인가 후인가, 이 셋이 한 틱에 몰아친 하나의 연쇄인가 몇 분 간격으로 벌어진 별개의 문제인가. 한 틱에 쏟아진 열 개는 열 개의 문제가 아니다.

순번은 단조 증가하는 정수로, 시계가 뒤로 가거나 같은 밀리초에 여러 건이 들어와도 순서가 흔들리지 않게 한다. 시각은 사람에게 보여주기 위한 것이고, 순번은 정렬과 반복 접기의 기준이다.

Layer A를 건드리는 유일한 변경이며, `boad`가 레코드를 만들 때 채운다.

### 3.5 같은 실패의 반복은 한 줄로 접는다

같은 사이트 태그가 200번 터지면 목록이 200줄이 되고, 그 아래 깔린 **다른** 실패 — 대개 진짜 원인 — 는 보이지 않는다. 스크롤로 원인을 찾게 만드는 것은 이 서브시스템의 목적에 정면으로 어긋난다.

연속된 같은 사이트 태그는 한 행으로 접고 `×47`처럼 횟수와 **처음·마지막 시각**을 함께 보여준다. 접힌 행을 펼치면 개별 발생을 볼 수 있다.

접기는 프레젠터가 한다 — Maya도 UI도 모르는 순수 판단이므로 gtest로 덮인다.

### 3.6 크래시를 건너 살아남는 저널

지금은 크래시가 나면 인메모리 스트림이 통째로 사라지고, "이 세션이 비정상 종료했다"는 사실조차 다음 실행이 알 수 없다. 정작 가장 알고 싶은 사건이 아무것도 남기지 않는다.

감시자 프로세스 없이도 **기록의 보존**은 할 수 있다. 실시간 분석은 Layer C의 몫이지만, 크래시 직전에 무슨 일이 있었는지는 저널로 남는다.

**부담을 지지 않는 근거.** 매 레코드마다 `fsync`를 부르면 그것이 진짜 부담이다. 하지만 크래시 포렌식에는 필요 없다 — 파일에 append한 내용은 커널 페이지 캐시가 들고 있고, **프로세스가 죽어도 OS가 그것을 디스크에 쓴다.** 잃는 것은 기계 전원이 나갈 때뿐이고, 그건 이 서브시스템이 대비하는 사건이 아니다. 따라서 저널은 열어둔 핸들에 한 줄 append하는 것이 전부다.

| 결정 | 내용 |
|---|---|
| 형식 | append-only JSONL. 플러그인 로드 시 한 번 열고 언로드까지 유지 |
| 위치 | `book`과 같은 디렉터리 (`bookPaths()`의 해소 결과를 재사용 — 테스트 재정의도 그대로 따라온다) |
| 쓰는 시점 | 발생 즉시, 동기적으로. 전용 뮤텍스로 보호하며 그 뮤텍스는 **말단**이다 — 안에서 `boad`도 `book`도 부르지 않으므로 잠금 순서 문제가 생기지 않는다 |
| `fsync` | 하지 않는다. 위 근거 |
| 세션 표식 | 로드 시 새 세션 줄, 정상 `uninitializePlugin`에서 종료 줄. **종료 줄 없이 끝난 세션이 곧 비정상 종료다** |

**반복은 저널에도 쓰지 않는다.** 같은 (심각도 + 사이트 태그)가 연속으로 나면 몇 줄까지만 쓰고 멈춘다. 그 연속이 끝날 때 몇 개를 생략했는지 한 줄로 남긴다. `compute()`의 경고가 매 평가마다 터지는 상황이 초당 수백 줄의 디스크 쓰기가 되는 것을 이것이 막는다 — §3.5의 화면 접기와 같은 판단을 저널에도 적용하는 것이다.

**저널도 무한히 자라면 안 된다.** Layer A가 인메모리 스트림에서 그 함정에 빠졌고 이 스펙 §5가 그 증상을 막고 있다. 저널은 최근 세션 몇 개만 유지하고 오래된 것부터 버린다. 로드 시 한 번 정리한다.

**다음 로드 때 무엇을 하나.** 마지막 세션이 종료 줄 없이 끊겼으면 그 세션의 저널 꼬리를 읽어 패널에 **"지난 세션이 비정상 종료했습니다"** 항목으로 복원한다. 사용자는 크래시 직전 진단을 그대로 볼 수 있다.

**하지 않는 것.** 저널은 기록을 보존할 뿐 크래시의 원인을 판정하지 않는다. 스택도, 예외 정보도, 어느 모듈이 죽였는지도 모른다. 그건 `offix`의 일이고 Layer C다. 다만 원 스펙(`2026-08-14-maro-troubleshooting-ecosystem-design.md`) §5.1이 감시자를 못 띄웠을 때의 최하위 폴백으로 이미 디스크 저널을 요구하고 있다 — 그 자리에 들어갈 형식이 바로 이것이므로, 나중에 감시자가 붙어도 여기서 만든 것이 버려지지 않는다.

### 3.7 상시 메인 스레드 큐

`MaroMainThreadQueue`를 플러그인 로드 시 설치하고 언로드 시 뗀다. 0.1초 주기의 `MTimerMessage`이며, 쌓인 작업을 비운다.

**`MaroPump`는 손대지 않는다.** 발행 펌프와 하나로 합치는 편이 구조적으로는 깔끔하지만, 그러려면 돌아가는 발행 코드를 고쳐야 하고 `MaroPump::isRunning()`의 의미가 바뀌어 `maroBridgeStats`와 기존 테스트의 관측값이 걸린다. 보조 유틸리티를 위해 본체 동작에 회귀 위험을 지는 것은 §1의 우선순위에 어긋난다. 독립된 타이머 하나가 더 도는 비용은 무시할 수 있다.

큐가 상시로 도는 덕분에 **브리지가 꺼져 있어도** 해법 적용이 안전한 시점을 얻는다. 진단은 보통 브리지를 켜기 전에 하므로 이것이 실제 경로다.

## 4. 해법

### 4.1 두 필드

`BookEntry`에 `remedyAction`을 기존 `remedy` 옆에 추가한다.

| 필드 | 내용 |
|---|---|
| `remedy` | 사람이 읽는 문장. **무엇을 바꿀지 설명한다** (원 스펙 §4.3 규칙 1) |
| `remedyAction` | 실행할 구조화된 동작. 없으면 설명만 있는 항목 |

둘을 나누면 이미 쓰인 book 항목이 그대로 유효하고(동작 없는 항목이 된다), 설명과 실행이 어긋날 수 없다.

`remedyAction`은 임의 코드가 아니다. `book` 파일은 Layer C에서 **감시자 프로세스가 쓰게** 되고 스필은 사용자 앱 디렉터리에 있다. 해법이 MEL/Python 스니펫이라면 그 파일을 쓸 수 있는 무엇이든 Maya 안에서 코드를 실행하게 된다. 구조화된 동작은 그 경로를 원천적으로 막는다.

### 4.2 동작 3종

실제로 존재하는 실패 사이트 태그에서 뽑았다.

| 동작 | 인자 | 덮는 실패 |
|---|---|---|
| `selectNode` | 노드 이름 | `TargetNotTransform`(셰이프 대신 transform 선택), `NotMaroAxisNode`, `SelfParent` |
| `setAttribute` | 노드, 어트리뷰트, 값 | `InvalidControlMode` |
| `disconnect` | 소스 플러그, 대상 플러그 | `AxisAlreadyBound`, `ObjectAlreadyHasAxis`, `WouldCreateCycle` |

`selectNode`는 씬을 편집하지 않는다 — 사용자를 올바른 노드로 데려다줄 뿐이다. 나머지 둘은 실제 편집이므로 `MDGModifier`를 거친다.

### 4.3 적용 불가가 일급 케이스다

실패 목록의 상당수는 **씬 편집으로 고칠 수 있는 것이 아니다.** `WrongArgCount`는 인자를 잘못 쓴 것이고, `NodeNotFound`는 이름 오타이며, `RuntimeStartFailed`·`PumpStartFailed`·`CreateMemoryPoolsFailed`는 환경 문제다.

이 경우 패널은 분석과 설명까지만 보여주고 **적용 버튼을 아예 내보내지 않는다.** 누를 수 없는 버튼을 회색으로 띄우는 것보다, 이 실패에는 기계적 해법이 없다는 사실을 말하는 편이 정확하다.

프레젠터는 버튼을 못 쓰는 이유를 구분해 내보낸다: 동작이 없음 / 대상 노드가 사라짐 / 지원하지 않는 동작 종류.

### 4.4 빈 컨텍스트와 포착 못 한 컨텍스트는 다르다

`DgContext`의 필드가 비어 있는 것은 두 가지 뜻일 수 있다 — 그 자리에 관여한 노드가 애초에 없었거나, 관여는 했는데 그 시점에 알아낼 수 없었거나.

후자가 실제로 있다. Layer A의 `MaroPump::onTimer`는 축들을 순회하다 터지면 몇 번째 축이었는지를 이미 잃은 뒤라 노드 타입만 채운다. `compute()` 계열은 워커 스레드일 때 Maya에 이름을 물을 수 없어 이름 칸을 비운다.

패널이 이 둘을 똑같이 빈칸으로 그리면 사용자는 "정보가 없다"와 "이 시스템이 고장 났다"를 구분하지 못한다. 원인 보고에서 그건 치명적이다. 프레젠터는 **"해당 없음"과 "이 자리에서는 포착되지 않음"을 다른 문구로** 내보내고, 후자에는 왜인지도 함께 붙인다(예: 평가 스레드에서 발생).

### 4.5 적용 경로

```
사용자가 [적용] 클릭
  → maroDiagRequestRemedy -index N   (큐에 넣기만 한다)
  → 다음 큐 틱 (DG 평가 중이 아님이 보장되는 시점)
  → MGlobal::executeCommand("maroApplyRemedy -index N")
  → 평범한 MPxCommand: MDGModifier로 수행, undo 스택에 오름
  → 적용 전후를 boad에 기록
```

**미루는 것은 커맨드 안이 아니라 커맨드의 호출 시점이다.** 커맨드 자신이 비동기로 동작하면 `doIt`이 아무것도 안 한 채 반환하면서 Maya의 undo 큐에 빈 항목이 올라간다. 위 구조에서 `maroApplyRemedy`는 완전히 평범하고 동기적이며 되돌릴 수 있는 커맨드다 — 큐는 그것을 **언제 부를지**만 정한다.

원 스펙 §4.3의 안전 규칙 넷이 모두 여기서 지켜진다: 제시가 기본이고 적용은 버튼, 적용은 `MPxCommand` 경유, 안전한 시점에만 실행, 전후를 기록.

## 5. 실패와 경계 조건

**패널이 열린 채 플러그인이 언로드되는 것**이 가장 위험하다. Maya가 언로드된 코드 안의 UI를 계속 붙들고 있으면 크래시한다. `uninitializePlugin`에서 `workspaceControl -e -close`로 확실히 닫는다. devkit `workspaceControlCmd` 샘플이 같은 이유로 같은 일을 한다.

반대 방향도 있다. Maya는 시작 시 **플러그인이 로드되기 전에** workspaceControl을 복원하려 든다. `-requiredPlugin`과 `-uiScript`로 처리한다.

| 상황 | 동작 |
|---|---|
| 패널이 닫혀 있거나 한 번도 안 열림 | 진단은 그대로 돈다. 스냅샷 단계는 아무 일도 하지 않는다. UI는 소비자이지 경로가 아니다 |
| 클릭과 실행 사이에 씬이 바뀜 | 실행 직전 재확인에서 걸러내고 `MDGModifier`를 되돌린 뒤 boad에 기록한다. 씬은 그대로다 |
| `book`을 못 읽음 | 행은 다 보이되 "전에 본 문제" 표시와 해법이 없다. Layer A가 이미 그렇게 강등한다 |
| 레코드가 무한히 쌓임 | **필터를 적용한 뒤** 최근 500개를 렌더링하고, 몇 개가 숨겨졌는지 명시한다 |
| 저널 파일을 열 수 없음 | 진단은 그대로 돈다. `book`이 못 쓸 때와 같은 규율이다 — 보존이 안 될 뿐 기능이 죽지 않는다. 세션당 한 번만 알린다 |
| 저널이 무한히 자람 | 최근 세션 몇 개만 남기고 로드 시 정리한다 (§3.6) |

마지막 항목은 Layer A에서 상한도 축출도 없이 이월한 것이 Layer B에서 만기되는 지점이다. B-1은 스트림 자체를 고치지 않는다 — 패널이 그리는 양만 제한한다. 스트림에 상한을 두는 것은 `boad`의 결정이고, 그때는 "오래된 진단이 사라져도 되는가"를 따로 답해야 한다.

**절단 순서가 중요하다.** 최근 500개를 먼저 자르고 나서 필터를 걸면, 연쇄의 **시작** — 진단에서 가장 중요한 한 줄 — 이 뒤따라온 수백 개의 반복에 밀려 사라진다. 그래서 순서는 반대다: 심각도 필터를 먼저 적용하고, 같은 사이트 태그의 반복을 접고(§3.5), 그러고도 500개가 넘으면 자른다. 에러만 걸고 반복을 접으면 대개 수십 줄로 줄어들어 절단 자체가 일어나지 않는다.

숨겨진 개수는 "표시되지 않음"이 아니라 **몇 개가 왜 숨겨졌는지**를 말한다. 필터로 빠진 것과 500개 상한으로 잘린 것은 다른 사건이다.

## 6. 검증

| 대상 | 방식 | 못 박는 것 |
|---|---|---|
| 프레젠터 | gtest (`maro_diag_tests`) | 행 구성, 심각도 매핑, 상세 조립, 적용 가능 여부와 **그 이유의 구분** |
| 원인 보고 규칙 | gtest (`maro_diag_tests`) | 반복 접기가 **다른 실패를 가리지 않는지**, 절단이 필터·접기 **뒤에** 오는지, 순번이 정렬 기준인지, "해당 없음"과 "포착 안 됨"이 다른 문구인지 |
| 적용 커맨드 | mayapy | 큐로 미뤄져 실행되는지, **`Ctrl+Z`로 되돌아가는지**, 전후가 boad에 남는지, 사라진 노드에서 씬이 안 변하는지 |
| 상시 큐 | mayapy | 브리지 없이 도는지, 브리지를 켜도 발행이 그대로인지 |
| 동작 3종 | mayapy | 각각이 실제로 의도한 변화를 만드는지, `selectNode`가 씬을 편집하지 않는지 |
| 저널 | mayapy (프로세스 둘) | 1번 프로세스가 진단을 남기고 **종료 줄 없이 죽으면**, 2번 프로세스가 비정상 종료를 감지하고 그 꼬리를 복원하는지 |
| 저널 반복 억제 | gtest | 같은 태그 연속 N개 뒤로는 줄이 안 늘고, 연속이 끝날 때 생략 개수가 남는지 |

저널의 크래시 시나리오는 Layer A의 `test_diag_book_cross_session.py`가 이미 쓰는 방식 — 자식 `mayapy` 둘 — 으로 만든다. 1번 프로세스는 정상 종료 대신 **종료 줄을 쓰기 전에 프로세스를 끊는다.** 감시자 입장에서 진짜 크래시와 구분되지 않는 신호이며, 원 스펙 §7의 "컴퓨터를 죽이지 않는다" 원칙 그대로다.

새로 넣는 테스트는 전부 **일부러 구현을 깨서 실패하는 것까지 확인**한다. 이 프로젝트에서 통과하던 테스트가 틀린 구현도 함께 통과시킨 경우가 열 번 있었고, 매번 그렇게만 잡혔다.

**자동화되지 않는 것을 명시한다.** `mayapy` 배치 모드에는 UI가 없어 `workspaceControl`이 성립하지 않는다. 도킹, 재시작 시 복원, 패널을 연 채 언로드하기 — 이 셋은 인터랙티브 Maya에서 사람이 확인해야 하며, 짧은 체크리스트로 문서화한다. 커버리지가 있는 척하지 않는다.

## 7. B-2가 싸게 붙기 위해 B-1이 지킬 것

- `PanelView`와 `ApplyIntent`에 **Maya UI든 Qt든 어떤 것도 등장하지 않는다**
- 패널을 여는 커맨드는 어느 판을 띄울지 고르는 **분기점 하나**를 갖는다. B-1에서는 선택지가 하나뿐이다
- 선택은 Maya `optionVar`에 저장한다. 키 이름을 B-1에서 정해두고, B-1은 그것을 읽되 값이 없으면 네이티브 판을 쓴다

**두 판을 가르는 근거는 성능이 아니라 호환성이다.** 진단 패널은 Maya 2026을 돌리는 기계에 부담이 되는 물건이 아니다. RAM이나 코어 수를 재서 추천하는 코드는 판단하는 것처럼 보이지만 실제로 아무것도 판단하지 않는다. 실제로 갈리는 것은 이 설치본에 Qt 판이 포함돼 있는가, 그리고 이 Maya의 Qt 버전이 그것과 맞는가다. B-2의 안내는 그 두 가지를 확인해 답한다.

참고로 이 머신에서는 devkit `Qt.zip`이 Qt 6.5.3을 담고 있고 Maya 2026의 `Qt6Core.dll`도 6.5.3.0이다 — 맞는다. `qoffscreen.dll`도 양쪽에 있어 B-2의 뷰는 자동 검증이 가능하다.

## 8. Layer A에서 이월된 것과의 관계

| 이월 항목 | B-1에서 |
|---|---|
| 레코드에 시각·순번 없음 | **B-1이 Layer A를 고쳐 채운다.** 원인 보고의 토대라 미룰 수 없다 |
| 크래시가 나면 인메모리 스트림이 통째로 사라짐 | **저널로 보존한다** (§3.6). 원인 판정은 여전히 Layer C |
| 비정상 종료를 다음 실행이 알 방법이 없음 | 세션 종료 줄의 부재로 감지한다 |
| `book`이 해시당 한 건만 들고 있어 발생 이력이 없음 | `book`은 그대로 둔다. 이력은 저널이 갖는다 — 둘의 역할이 다르다: `book`은 "이 자리에서 배운 것", 저널은 "이 세션에서 일어난 일" |
| 레코드 스트림에 상한·축출 없음 | 패널이 필터·접기 뒤 500개로 제한해 **증상만** 막는다. 원인은 그대로 |
| `MaroPump::onTimer`와 `compute()`가 컨텍스트를 부분적으로만 채움 | 채우지는 못한다. 대신 **비었다는 것과 못 채웠다는 것을 구분해 보여준다** (§4.4) |
| 등록된 해법이 스크립트 에디터 한 줄로만 나감 | 패널이 정식 소비자가 된다 |
| 캐시된 해시가 세션 내내 디스크를 다시 안 봄 | 그대로 둔다. 감시자가 정본을 쓰는 Layer C에서 만기된다 |
| `maroDiagCount`/`maroDiagQuery`가 테스트 전용 | **그대로 테스트 전용으로 남는다.** 패널은 전용 커맨드로 읽으므로 이 둘을 정식 계약으로 승격시킬 필요가 없다 |
