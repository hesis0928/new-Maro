# Maro 디버그 터미널 — boad 콘솔 에코에 진단 구분선 추가 (2026-09-02)

## 1. 배경

원 설계 문서(`2026-08-24-maro-main-ui-phase0-1-design.md` §7)는 "Phase 6 — 디버그 터미널(`python/maroTerminal.py`, 기존 4개 진단 커맨드 그대로 재사용)"을 로드맵 항목으로 남겨 뒀다. 이 항목을 브레인스토밍하며 `src/maro_plugin/MaroDiag.cpp`를 직접 확인한 결과, 로드맵이 가정했던 목표("진단이 자동으로, 별도로 열 필요 없이 노출된다")는 **이미 완전히 구현돼 있었다**:

`BoadMaro::info()`/`warn()`/`devInfo()`/`error()` — boad의 단일 출구(설계 스펙 `2026-08-14-maro-troubleshooting-ecosystem-design.md` §4 boad 행) — 는 메인 스레드에서 호출될 때마다 이미 `MGlobal::displayInfo`/`displayWarning`/`displayError`로 `[Maro-Info]`/`[Maro-Warn]`/`[Maro-Dev]`/`[Maro-Error]`/`[Maro-Fix]` 접두사를 붙여 Maya의 Script Editor 출력창에 즉시 에코한다. 진단이 생길 때마다 매번 찍히며(억제·뭉개기 없음), 새 창이나 별도 커맨드가 전혀 필요 없다.

즉 로드맵의 "디버그 터미널" 항목은 사실상 이미 완결돼 있었고, 실제로 비어 있는 것은 사용자가 지목한 딱 한 가지 — **연속된 진단 블록 사이의 시각적 구분선**뿐이다. 지금은 진단 하나당 한 줄(에러+해법이 있으면 두 줄)만 찍히고 끝나서, Script Editor를 스크롤할 때 어디까지가 한 진단이고 어디부터 다음 진단인지 구분되지 않는다.

이 문서는 그 구분선 하나만 다룬다. 새 UI 파일, 새 C++ 커맨드, 새 메뉴 항목은 전혀 필요 없다.

## 2. 사용자가 확정한 결정

1. 노출 방식: 창/패널을 새로 여는 게 아니라, 지금처럼 Maya Script Editor에 실시간·자동으로 찍히는 방식을 그대로 유지한다(이미 구현됨, 변경 대상 아님).
2. 구분선 내용: `------------` (하이픈 12개).
3. 적용 범위: `info`/`warn`/`devInfo`/`error` 네 심각도 전부에 동일하게 적용한다(일관성을 위해, warn/error만으로 한정하지 않는다).

## 3. 설계

**대상 파일**: `src/maro_plugin/MaroDiag.cpp`만 수정한다. `BoadMaro::info()`, `warn()`, `devInfo()`, `error()` 네 함수 각각의 기존 `if (isMainThread()) { ... }` 블록 끝에, 그 진단 한 건의 콘솔 에코가 전부 끝난 뒤 구분선 한 줄을 추가로 찍는다:

```cpp
if (isMainThread()) {
    MGlobal::displayWarning(MString("[Maro-Warn] ") + message);
    MGlobal::displayInfo(MString("------------"));   // 신규
}
```

`error()`는 `[Maro-Error]` 줄 다음에 (해법이 등록돼 있으면) `[Maro-Fix]` 줄까지 찍은 **뒤에** 구분선을 정확히 한 번만 찍는다 — 표시 호출 하나당이 아니라 진단 이벤트 하나당 구분선 하나. `devInfo()`는 `_DEBUG` 빌드에서만 본문이 컴파일되므로(이 프로젝트의 기본 빌드 구성인 RelWithDebInfo에서는 무연산), 구분선도 자연히 같은 조건 안에 들어간다 — 별도 분기가 필요 없다.

구분선은 레코드 자신의 심각도와 무관하게 항상 `MGlobal::displayInfo(...)`로 찍는다. 에러/경고 색으로 찍으면 "메시지의 일부"처럼 보이지만, 항상 기본색(displayInfo)으로 찍으면 "메시지가 아니라 구분자"라는 게 Maya의 기본 색 규칙에서 공짜로 드러난다 — `error()`가 이미 해법(`[Maro-Fix]`)을 에러와 다른 색으로 분리해 낸 것과 같은 근거(`MaroDiag.cpp:558-563`의 기존 주석 참고).

메인 스레드 가드는 기존 것을 그대로 재사용한다 — 워커 스레드(Maya 2026 Parallel Evaluation Manager 아래 `compute()` 등)에서는 지금처럼 콘솔 에코 자체(이번 구분선 포함)를 건너뛰고, 레코드는 그대로 인메모리 스트림/저널에 남는다. 새로운 스레드 안전성 문제는 생기지 않는다.

**정정(2026-09-02, 전체 브랜치 리뷰에서 발견)**: 아래 문단은 당초 "boad를 거치는 모든 호출부는 전부 이 4개 함수를 통해서만 콘솔로 나간다"고 썼으나, 이는 *예전에 boad로 마이그레이션된 72곳*에 대해서만 참이다. 실측 결과 `src/maro_plugin/` 안에는 애초에 boad를 거치지 않고 `MGlobal::displayError` 등을 여전히 직접 호출하는 자리가 약 50곳 남아 있다(예: `MaroRemedyCommands.cpp`, `MaroPanelCommands.cpp`, `MaroRosProxyCommands.cpp`, `MaroPythonBridge.cpp`) — 그 자리들은 이번 변경으로 구분선을 얻지 못한다. 좁게 참인 주장은 "boad의 네 진입점을 거치는 호출부는 전부 이 변경 하나로 구분선을 갖는다"이며, 이번 태스크의 범위는 정확히 거기까지다. 나머지 직접 호출 자리들을 boad로 옮기는 것은 별도의(더 큰) 후속 작업이다.

boad를 거치는 호출부(예전에 흩어져 있던 72곳의 `MGlobal::display*` 직접 호출을 이 4개 함수로 이미 마이그레이션해 둔 것, `MARO_ASSERT` 등 포함)는 전부 이 4개 함수를 통해서만 콘솔로 나가므로, 이 변경 하나로 그 호출부 전체가 자동으로 구분선을 갖게 된다 — 이게 애초에 boad를 "단일 출구"로 설계해 둔 이유(`MaroDiag.h:58` 기존 주석). 이 단일 출구 설계는 boad로 마이그레이션된 호출부에 대해서만 보장이며, boad 바깥에서 여전히 직접 `MGlobal::display*`를 부르는 자리에는 적용되지 않는다(위 정정 참고).

## 4. 테스트 전략

이 변경은 새로운 데이터나 상태를 만들지 않는다 — 콘솔에 문자열 한 줄을 더 찍는 순수 부작용이며, `DiagRecord`/스트림/저널/book 어느 쪽도 건드리지 않는다. 그래서:

- 기존 회귀 스위트(`ctest --test-dir out/build -C Release --output-on-failure`) 전체가 그대로 통과하는 것으로 충분하다 — 이 네 함수는 이미 수많은 기존 테스트(진단 emit, remedy, 저널 등)가 경유하는 경로이므로, 구분선 추가가 예외를 던지거나 기존 흐름을 깨지 않는다는 것을 회귀로 확인한다.
- 구분선이 Script Editor에 실제로 원하는 모양(정확히 한 진단 이벤트 뒤에 한 줄)으로 보이는지는 이 프로젝트가 반복해 온 대로 수동 확인 항목으로 남긴다(`docs/maro-panel-manual-checklist.md`에 새 절 추가) — 아무 Maro 진단(예: 잘못된 축 바인딩 시도, 존재하지 않는 노드에 커맨드 호출 등)을 연속으로 두 번 이상 일으켜, 각 블록이 `------------`로 나뉘어 보이는지, 그리고 해법이 있는 에러의 경우 `[Maro-Error]`+`[Maro-Fix]`가 한 블록으로 묶이고 그 뒤에만 구분선이 오는지 확인한다.

## 5. 범위 밖

- `python/maroTerminal.py`나 그 어떤 새 UI 패널도 만들지 않는다 — 콘솔 에코가 이미 그 역할을 하고 있다는 게 이번 조사의 핵심 결론이다.
- `maroMenu.py`에 새 메뉴 항목을 추가하지 않는다.
- 기존 `maroDiagPanel`(워크스페이스 컨트롤, 목록+상세+해법 적용)과의 통합/대체는 다루지 않는다 — 그 패널은 과거 진단을 훑고 해법을 적용하는 용도로 계속 별도로 존재하며, 이번 구분선은 그것과 무관하게 "지금 실시간으로 무슨 일이 있었는지" 채널만 다듬는다.
- 구분선 표시 여부를 끄고 켜는 설정(옵션)은 만들지 않는다 — 항상 켜져 있다.
