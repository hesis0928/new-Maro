# Maro 트러블슈팅 생태계 — 설계

작성일: 2026-08-14
상태: 승인 대기

## 1. 목적

**사용자가 무엇이 잘못됐는지 빠르게 알고, 왜 그런지를 제공받는 것이 이 서브시스템의 주목적이다.** 나머지는 전부 그것을 받치는 인프라다.

지금은 `MGlobal::displayError` 계열 호출 72곳이 각자 스크립트 에디터에 문자열 한 줄을 뱉고 끝난다. 사용자는 그 줄만 보고 원인을 스스로 추적해야 한다. 같은 문제를 두 번째 만나도 처음부터 다시 분석해야 하고, 플러그인이 비정상 종료하면 아무 기록도 남지 않는다.

이 설계가 사용자에게 주는 것:

- **원인까지 붙은 진단.** 에러 한 줄이 아니라 무엇이 얽혀서 생긴 문제인지 — 어느 노드, 어느 어트리뷰트, 어느 커맨드가 관여했는지 — 를 구조화해 보여준다
- **아는 문제는 즉답.** 에러를 해시로 식별하고 과거 분석을 영구 저장해, 두 번째 발생 시 다시 분석하지 않고 바로 꺼내 준다
- **알려진 문제는 고칠 방법까지.** 해법이 기록된 에러는 그것을 제시하고, 사용자가 승인하면 적용한다
- **죽어도 남는 기록.** 별도 감시자 프로세스가 플러그인보다 오래 살아 비정상 종료를 감지하고 분석하며, 시스템 셧다운 시 파편을 남겨 다음 기동 때 조립한다

앞의 세 가지가 제품이고, 마지막이 그것을 끊기지 않게 하는 장치다.

## 2. 범위

### 포함

- **진단 패널** — Maya 안의 도킹 가능한 UI. 진단 스트림, 원인 분석, 기지(旣知) 여부, 해법 제시
- **해법 적용(auto-fix)** — `book`에 기록된 해법을 적용. 승인 적용과 **자동 적용 모드**를 모두 지원한다 (§4.3)
- 감시자 프로세스 `maro_sentinel.exe` — 기동·통신·수명 관리
- 여섯 계층: `boad`(진단 출구 + UI), `book`(지식·해법 DB), `onfix`(DG 컨텍스트 포착), `offix`(크래시 분석), `ghost`(셧다운 대비·조립), `OSbridge`(시스템 로그)
- 플러그인의 `MGlobal::display*` 호출 72곳을 `boad` 경유로 전환
- 기존 `Maro_DebugUtility/` 정리 — 인코딩, 결합 해소, 빌드 편입

### 제외

- `maroLidar`(S4) — 독립 서브시스템, 별도 스펙
- **검증되지 않은 해법의 자동 적용** — 자동 적용은 지원하되, 그 대상은 사용자가 신뢰 표시한 해법으로 한정된다 (§4.3)

## 3. 아키텍처

### 3.1 두 프로세스

```
Maya 프로세스                          maro_sentinel.exe
┌─────────────────────┐               ┌──────────────────────┐
│ 플러그인            │               │ 감시자               │
│  boad ──┐           │  named pipe   │  offix   ghost       │
│  onfix ─┼── 부스러기├──────────────>│  OSbridge            │
│         │           │               │                      │
│  book(읽기)         │               │  book(쓰기)          │
└─────┬───────────────┘               └──────┬───────────────┘
      │                                      │
      └──────────► book 파일 ◄────────────────┘
                (양쪽 읽기 / 감시자만 쓰기)
```

### 3.2 파이프 끊김이 곧 크래시 신호

감시자와 플러그인을 명명된 파이프로 잇는다. **죽음을 판정하는 데 하트비트나 폴링을 쓰지 않는다.**

- 정상 종료 시 플러그인은 `uninitializePlugin`이 끝나기 **전에** `SESSION_END_CLEAN`을 보낸다
- 그 메시지 뒤에 파이프가 닫히면 → 정상 종료. 감시자도 정리하고 종료
- 그 메시지 **없이** 끊기면 → 크래시. `offix` 실행

Windows가 주는 신호이므로 "몇 초 무응답이면 죽은 것으로 친다" 같은 임의의 값이 설계에 들어가지 않는다.

### 3.3 행(hang)은 별개 진단이다

멈춘 프로세스는 파이프를 계속 열어 둔다. 따라서 파이프 끊김은 *죽음*을 정확히 잡지만 *행*은 못 잡는다. 둘은 다른 조건이므로 다른 수단으로 잡는다.

| 조건 | 수단 | 타임아웃 |
|---|---|---|
| 크래시 | 파이프 끊김 | 불필요 |
| 행 | 느린 하트비트 | 불가피 (행 감지의 본질) |

하트비트는 플러그인에 이미 30Hz로 도는 `MaroPump` 타이머에 얹는다. 추가 스레드가 없다.

### 3.4 부스러기 스트림

감시자는 Maya의 주소공간을 볼 수 없다. 그래서 플러그인이 진행하면서 컨텍스트를 파이프로 흘린다.

**모듈 태그를 붙여 보낸다.** 하나의 뭉치로 합치지 않는다 — §4.1의 3분할 파편이 모듈별 분담을 요구하기 때문이다. 감시자는 태그별로 분리해 보관하고, Maya가 이미 죽은 뒤에도 각 모듈 몫을 그 모듈 이름으로 기록할 수 있다.

| 태그 | 흘리는 내용 |
|---|---|
| `onfix` | 현재 활성 노드, 어트리뷰트, 진행 중인 커맨드 |
| `offix` | 최근 에러 해시, 반복 경고 |
| `boad` | 마지막 사용자 조작, 화면에 떠 있는 진단 |

감시자는 태그마다 **최신값만** 유지한다(누적하지 않는다). 크래시 시점에 이미 최종 상태를 모듈별로 손에 쥐고 있으므로, 죽은 프로세스를 뒤질 필요가 없다.

### 3.5 book은 읽기와 쓰기를 분리한다

`book`(에러 해시 → 과거 분석)은 파일이다.

- **읽기**: 플러그인과 감시자 양쪽이 직접 파일 접근
- **쓰기**: 감시자만

읽기까지 IPC로 보내면 감시자가 죽었을 때 과거 지식 조회가 통째로 멎는다. 직접 읽기로 두면 감시자 없이도 지식은 계속 나오고, 새 지식이 안 쌓일 뿐이다.

### 3.6 불변식 — 감시자는 순수하게 덧붙이는 것

> **감시자가 없으면 진단이 나빠질 뿐, 기능이 나빠지지 않는다.**

- 플러그인은 감시자를 기다리며 블로킹하지 않는다
- 파이프 쓰기는 전부 논블로킹
- 감시자가 없거나 먹통이면 로컬에 기록하고 그대로 진행

이 한 줄이 "진단을 붙였더니 본체가 불안정해졌다"를 구조적으로 막는다.

## 4. 계층 계약

`maro.cpp`의 원안은 데스크톱 애플리케이션을 상정해 쓰였다. 의도는 지키되 플러그인 맥락의 실물로 옮긴다.

| 계층 | 원안 | 이 설계에서의 실물 |
|---|---|---|
| **boad** | 사용자 UI 관제 | **진단 패널**(§4.2) + 진단의 단일 출구. 스크립트 에디터 출력 + 감시자 전달 + 에러 시 `book` 우선 조회 |
| **book** | 영구 지식 저장소 | 에러 해시 → 과거 분석. 파일 기반, 양쪽 읽기 / 감시자만 쓰기 |
| **onfix** | 디렉터리 인덱싱, 연관성 트리 | **DG 컨텍스트 포착.** 어느 노드 타입·어트리뷰트·커맨드·축이 얽혔는지를 구조화 |
| **offix** | 크래시 딥디버깅 | 감시자에서 실행. 보유한 부스러기 스트림으로 크래시 기록 생성 |
| **ghost** | 셧다운 대비·파편·조립 | 감시자에서 실행. 셧다운 신호 → 파편 저장 지휘, 다음 기동 시 조립 |
| **OSbridge** | 시스템 로그 플러시 | 실제 Windows 이벤트 로그. 소스 미등록 시(관리자 권한 필요) 파일로 강등 |

**`onfix`가 바뀐 이유**: 플러그인에서 에러의 원인은 파일 경로가 아니라 **노드와 어트리뷰트의 관계**에 있다. 연관성 트리를 만든다는 의도는 그대로이고, 트리의 노드가 파일에서 DG 요소로 바뀐다.

### 4.1 3분할 파편 — 모듈별 분담이 핵심이다

원안의 요지는 **세 모듈이 각자 자기 몫을 기록한다**는 것이다. 시간 압박 하에 한 모듈이 전부를 직렬화하느라 병목이 되지 않게 하려는 설계이고, 조각마다 출처가 달라야 조립본이 여러 각도를 담는다. 이 분담을 유지한다.

**경로 1 — Maya가 살아 있을 때 (시스템 셧다운의 통상 경우)**

`ghost`가 지휘하고 세 모듈이 **병렬로 각자 기록**한다. 원안 그대로다.

| 모듈 | 자기 몫 |
|---|---|
| `onfix` | 마지막 DG 컨텍스트 — 활성 노드, 어트리뷰트, 진행 중이던 커맨드 |
| `offix` | 직전 이상 징후 — 최근 에러 해시, 반복 경고, 비정상 패턴 |
| `boad` | 사용자 행위 맥락 — 마지막 사용자 조작과 화면에 떠 있던 진단 |

서로를 기다리지 않고 각자 자기 파일에 쓴다.

**경로 2 — Maya가 이미 죽었을 때**

플러그인 쪽 모듈이 쓸 수 없다. 그래서 **감시자가 모듈별로 분리된 상태를 계속 들고 있는다.** 부스러기 스트림을 하나의 뭉치로 합치지 않고 `onfix`/`offix`/`boad` 태그별로 나눠 보관하며, 셧다운 시 그 세 갈래를 각각 해당 모듈 이름으로 기록한다.

즉 **출처 분담은 두 경로 모두에서 보존된다.** 차이는 누가 펜을 쥐었느냐일 뿐이고, 조각의 성격과 귀속은 같다. 이 요구가 부스러기 스트림을 모듈 태그로 나눠 보내야 하는 이유이며, 설계상 타협 대상이 아니다.

**조립**

다음 기동 시 `ghost`가 세 조각을 읽어 하나의 기록으로 합치고, 원안대로 `onfix` → `offix` 순으로 누락분을 보강하게 한 뒤 `boad`로 송출한다.

### 4.2 진단 패널 (boad)

이 서브시스템의 주목적이 사용자의 빠른 원인 파악이므로, 패널은 곁가지가 아니라 제품의 얼굴이다.

Maya의 `workspaceControl`로 도킹 가능한 패널을 띄운다. devkit의 `workspaceControlCmd` 샘플이 그 방식을 보여준다.

**보여주는 것**

| 영역 | 내용 |
|---|---|
| 진단 스트림 | info / warn / error 를 심각도로 구분해 시간순으로 |
| 원인 분석 | 에러 선택 시 `onfix`가 포착한 DG 컨텍스트 — 어느 노드·어트리뷰트·커맨드·축이 얽혔는지 |
| 기지 여부 | `book`에 있는 에러면 "전에 본 문제"로 표시하고 과거 분석을 즉시 펼친다 |
| 해법 | 해법이 기록돼 있으면 그것과 **적용 버튼**을 함께 (§4.3) |

**설계 제약**

- 패널은 **자체 상태를 갖지 않는다.** `boad`가 보유한 진단 기록과 `book` 파일만 읽는다. S1+S2에서 확립한 "상태는 한 곳에" 원칙을 그대로 따른다
- UI 갱신은 **메인 스레드에서만.** 감시자나 백그라운드에서 온 항목은 기존 `MaroPump` 타이머를 통해 반영한다
- 패널이 닫혀 있어도 진단은 정상 동작한다. UI는 소비자이지 경로가 아니다

### 4.3 해법 적용 (auto-fix)

`book`은 에러 해시에 대해 과거 분석뿐 아니라 **해법**도 저장한다. 해법은 실행 가능한 형태(MEL/Python 스니펫 또는 정의된 수정 동작)로 기록된다.

#### 해법의 신뢰 단계

해법은 세 단계를 거친다. 자동 적용은 마지막 단계에서만 일어난다.

| 단계 | 상태 | 동작 |
|---|---|---|
| 1 | 해법 없음 | 원인 분석만 제공. 사용자가 해결하면 그 방법을 `book`에 등록할 수 있다 |
| 2 | 해법 있음 | 패널에 제시하고 **적용 버튼**을 띄운다. 사용자가 눌러야 적용 |
| 3 | 신뢰됨 | 자동 적용 모드가 켜져 있으면 **묻지 않고 적용**한다 |

2단계에서 적용해 문제가 해결되면 패널이 "이 해법을 신뢰함"을 제안하고, 사용자가 한 번 누르면 3단계로 올라간다. **자동 승격은 없다** — 몇 번 성공했다고 시스템이 스스로 신뢰 판정을 내리지 않는다.

이 단계 구조가 요점이다. "자동 적용 켜기"가 곧 "무엇이든 자동으로 고침"이 되지 않는다. 사용자가 직접 겪고 확인한 해법만 자동으로 돈다.

#### 자동 적용 모드

전역 토글로 켜고 끈다. 기본값은 꺼짐이다.

**적용 시에도 지키는 것**

- **`MPxCommand` 경유.** 자동이든 수동이든 undo 스택에 올라간다. Ctrl+Z로 되돌아간다
- **말없이 하지 않는다.** 자동 적용은 조용한 적용이 아니다. 패널에 눈에 띄게 표시하고 `boad`에도 남긴다. 사용자가 "언제 뭐가 바뀌었지"를 항상 추적할 수 있다
- **안전한 시점에만.** `compute()`나 콜백 안에서 씬을 고치지 않는다. 평가 중 DG를 건드리는 것은 S1+S2에서 이미 위험으로 확인된 지점이다. 자동 적용은 기존 `MaroPump` 타이머의 메인 스레드 시점으로 미뤄 실행한다
- **루프 차단.** 같은 해법이 짧은 시간에 반복 발동하면 그 해법의 자동 적용을 중단하고 사용자에게 알린다. 고치지 못하는 해법이 에러–수정–에러를 무한히 도는 것을 막는다
- **즉시 전역 정지.** 토글 하나로 자동 적용 전체가 멎는다. 무언가 잘못 돌고 있을 때 사용자가 붙잡을 손잡이가 필요하다

#### 왜 이렇게까지 하는가

진단 시스템이 사용자 몰래 데이터를 바꾸면 신뢰를 잃고, 한 번 잃으면 진단 자체를 꺼 버린다. 그러면 이 서브시스템의 주목적인 "빠른 원인 파악"까지 함께 사라진다.

위 제약들은 자동 적용을 막으려는 것이 아니라, **자동 적용이 계속 쓰이게 하려는 것**이다.

## 5. 위험과 회피

### 5.1 job object가 감시자를 함께 죽인다

Maya가 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`가 걸린 job 안에서 실행되면 자식 프로세스가 함께 종료되어 설계 전체가 무의미해진다. 3단계로 내려가되, **각 단계가 기능을 얼마나 보존하는지** 명시한다.

**1단계 — `CREATE_BREAKAWAY_FROM_JOB` + 실측 확인**

감시자가 기동 직후 `IsProcessInJob`으로 자기 상태를 확인해 파이프로 보고한다. "빠져나왔겠지"가 아니라 "빠져나왔다"를 안다.

**2단계 — WMI `Win32_Process::Create` 우회**

breakaway가 막히면 WMI로 생성한다. 프로세스가 Maya의 자식이 아니라 WMI 서비스 밑에서 만들어지므로 Maya의 job과 무관해진다. 같은 사용자 프로세스라 관리자 권한이 필요 없다.

**3단계 — 저널로 강등**

둘 다 막히면 플러그인이 디스크 저널을 남기고, **다음 플러그인 로드가 그것을 읽어 `offix` 분석을 수행**한다. 잃는 것은 분석 *시점*뿐(즉시가 아니라 다음 로드)이며 크래시 감지와 분석 자체는 살아 있다.

저널은 경쟁안이 아니라 **이 설계의 최하위 단계**다. 부스러기를 흘리려면 어차피 그 형식이 필요하므로 폴백 구현이 낭비되지 않는다.

### 5.2 감시자가 좀비가 된다

이 프로젝트가 네 번 겪은 실패 모드다(`mayapy.exe`가 `taskkill /F`와 `/T`를 90초 버티고 WMI `Terminate`로만 종료된 사례 포함). 다섯 겹으로 막는다.

- **모든 대기에 상한.** 무기한 블로킹이 한 군데도 없다. `WaitForMultipleObjects`에 종료 이벤트와 타임아웃을 항상 함께 건다
- **절대 수명.** 붙은 Maya 없이 일정 시간이 지나면 스스로 종료한다
- **명명된 뮤텍스로 단일 인스턴스.** 플러그인을 반복 로드해도 감시자가 떼로 생기지 않는다
- **PID를 찾을 필요 없는 킬 스위치.** 명명된 이벤트 하나로 즉시 종료한다
- **자기 PID·시작 시각을 알려진 파일에 기록.** 사람이 손으로 찾을 때 헤매지 않는다

여기에 더해 **플러그인 로드 시 자가 점검** — 붙을 Maya가 없는 낡은 감시자를 발견하면 종료시킨다.

### 5.3 감시자가 죽으면 플러그인이 오판한다

플러그인 쪽에서 파이프가 끊기는 것은 *감시자*가 죽었다는 뜻이다. 극적인 결론을 내리지 않고 "진단 오프라인"으로 기록한 뒤, 재기동을 **한 번만** 시도하고 계속 진행한다.

### 5.4 강등 중 지식 DB가 갈라진다

감시자가 죽어 플러그인이 로컬 기록으로 강등되면 두 갈래가 생긴다. 플러그인의 강등 기록은 **스필 파일**로 나가고 감시자가 다음 기동 때 흡수한다. 정식 DB의 단일 쓰기자 원칙이 유지된다.

## 6. 기존 코드 정리

`Maro_DebugUtility/`는 517줄이고 실체가 있으나 세 가지를 손봐야 한다.

- **CP949 인코딩** — 플러그인에서 이미 겪고 고친 것과 같은 문제. UTF-8로 변환한다
- **`BoadMaro::dumpState(const ViewportStreamer*)` 결합** — 로거가 특정 클래스에 묶여 있다. 헤더 주석도 옮기라고 적혀 있다. 일반 상태 제공자로 분리하거나 제거한다
- **빌드 누락** — 옛 colcon 트리에 `COLCON_IGNORE`로 방치되어 새 CMake가 전혀 모른다. `src/` 아래로 정식 편입한다

`offix_Maro.h`의 주석은 이미 "Out-of-Process 디버깅 분석 시뮬레이션"이라 되어 있다. 이 설계는 방향 전환이 아니라 원래 의도의 완성이다.

## 7. 검증 — 컴퓨터를 죽이지 않는다

| 시나리오 | 방법 |
|---|---|
| 크래시 감지 | 플러그인이 `SESSION_END_CLEAN` 없이 파이프 핸들을 닫는다. 감시자 입장에서 진짜 크래시와 구분되지 않는 신호 |
| 셧다운 대비 | 명명된 이벤트로 트리거를 주입한다. `WM_QUERYENDSESSION`이 왔을 때와 같은 경로 |
| **파편 분담 (Maya 생존)** | 셧다운 트리거 후 `onfix`/`offix`/`boad` 세 파일이 **각각** 생기고 내용이 서로 다른지 확인 |
| **파편 분담 (Maya 사망)** | 파이프를 끊은 뒤 셧다운 트리거. 감시자가 태그별 보관분으로 **여전히 세 파일을 모듈 이름으로** 쓰는지 확인 |
| 파편 조립 | 파편 파일을 손으로 써두고 감시자를 기동해 기대한 기록이 나오는지 확인 |
| **원인 분석 내용** | 에러를 유발하고 `onfix`가 포착한 DG 컨텍스트에 관여 노드·어트리뷰트가 실제로 담겼는지 확인. "무언가 기록됐다"가 아니라 값을 단언한다 |
| **기지 에러 즉답** | 같은 에러를 두 번 유발해, 두 번째는 재분석 없이 `book`에서 나오는지 확인 |
| **해법 적용과 undo** | 해법이 등록된 에러를 유발하고 적용한 뒤, Ctrl+Z로 되돌아가는지 확인 |
| **승인 없이 안 고침** | 해법이 있어도 **신뢰 표시 전**이면 사용자가 누르기 전까지 씬이 바뀌지 않는지 확인 |
| **자동 적용** | 신뢰 표시한 해법 + 토글 켬 상태에서 에러를 유발해, 묻지 않고 적용되고 undo도 되는지 확인 |
| **자동 적용이 조용하지 않음** | 자동 적용 후 패널과 `boad` 기록에 무엇이 언제 바뀌었는지 남는지 확인 |
| **신뢰 승격은 수동뿐** | 해법을 여러 번 성공 적용해도 사용자가 누르기 전에는 3단계로 올라가지 않는지 확인 |
| **루프 차단** | 고치지 못하는 해법을 신뢰 등록해 반복 발동시키고, 자동 적용이 스스로 멎으며 사용자에게 알리는지 확인 |
| **전역 정지** | 자동 적용 도중 토글을 끄면 즉시 멎는지 확인 |
| **패널 없이도 동작** | 패널을 닫은 상태에서 진단·기록이 정상인지 확인 |
| job 탈출 | 감시자의 `IsProcessInJob` 보고로 단언 |
| 좀비 없음 | 각 테스트 종료 후 감시자 프로세스가 남지 않는지 확인 |
| 강등 | 감시자를 죽인 상태에서 플러그인이 계속 동작하고 과거 지식 조회가 되는지 확인 |

선례가 있다 — 기존 `rosSimCmd.cpp`의 `-testShutdown` 플래그가 정확히 `ghost`의 두 함수를 부르고 있었다.

**새로 넣는 테스트는 전부 고의로 구현을 깨서 실패하는 것까지 확인한다.** 이 프로젝트에서 통과하던 테스트가 틀린 구현도 함께 통과시킨 경우가 일곱 번 있었고, 매번 그렇게만 잡혔다.

## 8. 향후 서브시스템과의 관계

- **`maroLidar` (S4)**: 이 생태계 위에서 진단된다. LiDAR 백그라운드 스레드의 오류도 `boad`를 거쳐 감시자로 가고, 진단 패널에 원인과 함께 뜬다
- **S3 (노드 그래프 에디터)**: 진단 패널과 같은 `workspaceControl` 기반이므로 UI 기반을 공유한다. 다만 에디터는 DG를 편집하고 패널은 진단을 읽기만 하므로 서로 독립적이다
- **지식의 축적**: 사용자가 스스로 해결한 방법을 패널에서 `book`에 등록할 수 있으므로, 이 생태계는 쓸수록 즉답률이 올라간다. 팀 단위로 `book` 파일을 공유하면 한 사람이 겪은 문제를 다른 사람이 겪지 않는다
