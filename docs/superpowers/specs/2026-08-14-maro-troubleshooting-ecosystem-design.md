# Maro 트러블슈팅 생태계 — 설계

작성일: 2026-08-14
상태: 승인 대기

## 1. 목적

Maro 플러그인의 진단을 하나의 체계로 묶는다. 지금은 `MGlobal::displayError` 계열 호출 72곳이 각자 스크립트 에디터에 문자열을 뱉고 끝난다. 같은 문제를 두 번째 만나도 처음부터 다시 분석해야 하고, 플러그인이 비정상 종료하면 아무 기록도 남지 않는다.

이 설계는 세 가지를 얻는다.

- **반복 문제의 즉답** — 에러를 해시로 식별하고 과거 분석을 영구 저장해, 두 번째 발생 시 바로 꺼내 준다
- **자기 죽음의 관찰** — 별도 감시자 프로세스가 플러그인보다 오래 살아, 비정상 종료를 감지하고 분석한다
- **셧다운 대비** — 시스템이 내려갈 때 진단 파편을 남기고, 다음 기동 때 조립한다

## 2. 범위

### 포함

- 감시자 프로세스 `maro_sentinel.exe` — 기동·통신·수명 관리
- 여섯 계층: `boad`(진단 출구), `book`(지식 DB), `onfix`(DG 컨텍스트 포착), `offix`(크래시 분석), `ghost`(셧다운 대비·조립), `OSbridge`(시스템 로그)
- 플러그인의 `MGlobal::display*` 호출 72곳을 `boad` 경유로 전환
- 기존 `Maro_DebugUtility/` 정리 — 인코딩, 결합 해소, 빌드 편입

### 제외

- `maroLidar`(S4) — 독립 서브시스템, 별도 스펙
- Qt 기반 진단 UI — `boad`는 이번에 스크립트 에디터와 감시자까지만. 시각적 관제판은 후속
- 자동 수정(auto-fix) — 분석과 기록까지. 고치는 것은 사람이 한다

## 3. 아키텍처

### 3.1 두 프로세스

```
Maya 프로세스                          maro_sentinel.exe
┌─────────────────────┐               ┌──────────────────────┐
│ 플러그인            │               │ 감시자               │
│  boad ──┐           │  named pipe   │  offix   ghost       │
│  onfix ─┼── 부스러기├──────────────>│  OSbridge            │
│         │           │               │                      │
│  book(읽기)         │               │  book(쓰기)          │
└─────┬───────────────┘               └──────┬───────────────┘
      │                                      │
      └──────────► book 파일 ◄────────────────┘
                (양쪽 읽기 / 감시자만 쓰기)
```

### 3.2 파이프 끊김이 곧 크래시 신호

감시자와 플러그인을 명명된 파이프로 잇는다. **죽음을 판정하는 데 하트비트나 폴링을 쓰지 않는다.**

- 정상 종료 시 플러그인은 `uninitializePlugin`이 끝나기 **전에** `SESSION_END_CLEAN`을 보낸다
- 그 메시지 뒤에 파이프가 닫히면 → 정상 종료. 감시자도 정리하고 종료
- 그 메시지 **없이** 끊기면 → 크래시. `offix` 실행

Windows가 주는 신호이므로 "몇 초 무응답이면 죽은 것으로 친다" 같은 임의의 값이 설계에 들어가지 않는다.

### 3.3 행(hang)은 별개 진단이다

멈춘 프로세스는 파이프를 계속 열어 둔다. 따라서 파이프 끊김은 *죽음*을 정확히 잡지만 *행*은 못 잡는다. 둘은 다른 조건이므로 다른 수단으로 잡는다.

| 조건 | 수단 | 타임아웃 |
|---|---|---|
| 크래시 | 파이프 끊김 | 불필요 |
| 행 | 느린 하트비트 | 불가피 (행 감지의 본질) |

하트비트는 플러그인에 이미 30Hz로 도는 `MaroPump` 타이머에 얹는다. 추가 스레드가 없다.

### 3.4 부스러기 스트림

감시자는 Maya의 주소공간을 볼 수 없다. 그래서 플러그인이 진행하면서 컨텍스트를 파이프로 흘린다.

- 마지막으로 실행된 커맨드
- 현재 활성 노드
- 마지막 에러 해시

감시자는 각 항목의 **최신값만** 유지한다(누적하지 않는다). 크래시 시점에 이미 최종 상태를 손에 쥐고 있으므로, 죽은 프로세스를 뒤질 필요가 없다.

### 3.5 book은 읽기와 쓰기를 분리한다

`book`(에러 해시 → 과거 분석)은 파일이다.

- **읽기**: 플러그인과 감시자 양쪽이 직접 파일 접근
- **쓰기**: 감시자만

읽기까지 IPC로 보내면 감시자가 죽었을 때 과거 지식 조회가 통째로 멎는다. 직접 읽기로 두면 감시자 없이도 지식은 계속 나오고, 새 지식이 안 쌓일 뿐이다.

### 3.6 불변식 — 감시자는 순수하게 덧붙이는 것

> **감시자가 없으면 진단이 나빠질 뿐, 기능이 나빠지지 않는다.**

- 플러그인은 감시자를 기다리며 블로킹하지 않는다
- 파이프 쓰기는 전부 논블로킹
- 감시자가 없거나 먹통이면 로컬에 기록하고 그대로 진행

이 한 줄이 "진단을 붙였더니 본체가 불안정해졌다"를 구조적으로 막는다.

## 4. 계층 계약

`maro.cpp`의 원안은 데스크톱 애플리케이션을 상정해 쓰였다. 의도는 지키되 플러그인 맥락의 실물로 옮긴다.

| 계층 | 원안 | 이 설계에서의 실물 |
|---|---|---|
| **boad** | 사용자 UI 관제 | 진단의 단일 출구. 스크립트 에디터 출력 + 감시자 전달 + 에러 시 `book` 우선 조회 |
| **book** | 영구 지식 저장소 | 에러 해시 → 과거 분석. 파일 기반, 양쪽 읽기 / 감시자만 쓰기 |
| **onfix** | 디렉터리 인덱싱, 연관성 트리 | **DG 컨텍스트 포착.** 어느 노드 타입·어트리뷰트·커맨드·축이 얽혔는지를 구조화 |
| **offix** | 크래시 딥디버깅 | 감시자에서 실행. 보유한 부스러기 스트림으로 크래시 기록 생성 |
| **ghost** | 셧다운 대비·파편·조립 | 감시자에서 실행. 셧다운 신호 → 파편 저장 지휘, 다음 기동 시 조립 |
| **OSbridge** | 시스템 로그 플러시 | 실제 Windows 이벤트 로그. 소스 미등록 시(관리자 권한 필요) 파일로 강등 |

**`onfix`가 바뀐 이유**: 플러그인에서 에러의 원인은 파일 경로가 아니라 **노드와 어트리뷰트의 관계**에 있다. 연관성 트리를 만든다는 의도는 그대로이고, 트리의 노드가 파일에서 DG 요소로 바뀐다.

### 4.1 3분할 파편의 의미

원안에서 `ghost`가 파편을 셋으로 나눠 저장하는 것은, 시간 압박 하에 한 모듈이 전부를 직렬화하느라 병목이 되지 않게 하려는 설계다. 두 프로세스 구조에서도 그 의미는 살아 있다 — 감시자의 부스러기 뷰, `book`의 미기록분, `OSbridge`의 예측이 **서로를 기다리지 않고 독립적으로** 나간다.

다만 정직하게 적어 둔다: 셧다운 시점에 Maya는 이미 죽어 있을 수 있다. 그때 파편의 출처는 감시자가 보유한 것과 플러그인이 마지막으로 흘린 것이다. 조립 결과가 쓸모 있으면 되고, 세 조각이 각각 살아 있는 모듈에서 나올 필요는 없다.

## 5. 위험과 회피

### 5.1 job object가 감시자를 함께 죽인다

Maya가 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`가 걸린 job 안에서 실행되면 자식 프로세스가 함께 종료되어 설계 전체가 무의미해진다. 3단계로 내려가되, **각 단계가 기능을 얼마나 보존하는지** 명시한다.

**1단계 — `CREATE_BREAKAWAY_FROM_JOB` + 실측 확인**

감시자가 기동 직후 `IsProcessInJob`으로 자기 상태를 확인해 파이프로 보고한다. "빠져나왔겠지"가 아니라 "빠져나왔다"를 안다.

**2단계 — WMI `Win32_Process::Create` 우회**

breakaway가 막히면 WMI로 생성한다. 프로세스가 Maya의 자식이 아니라 WMI 서비스 밑에서 만들어지므로 Maya의 job과 무관해진다. 같은 사용자 프로세스라 관리자 권한이 필요 없다.

**3단계 — 저널로 강등**

둘 다 막히면 플러그인이 디스크 저널을 남기고, **다음 플러그인 로드가 그것을 읽어 `offix` 분석을 수행**한다. 잃는 것은 분석 *시점*뿐(즉시가 아니라 다음 로드)이며 크래시 감지와 분석 자체는 살아 있다.

저널은 경쟁안이 아니라 **이 설계의 최하위 단계**다. 부스러기를 흘리려면 어차피 그 형식이 필요하므로 폴백 구현이 낭비되지 않는다.

### 5.2 감시자가 좀비가 된다

이 프로젝트가 네 번 겪은 실패 모드다(`mayapy.exe`가 `taskkill /F`와 `/T`를 90초 버티고 WMI `Terminate`로만 종료된 사례 포함). 다섯 겹으로 막는다.

- **모든 대기에 상한.** 무기한 블로킹이 한 군데도 없다. `WaitForMultipleObjects`에 종료 이벤트와 타임아웃을 항상 함께 건다
- **절대 수명.** 붙은 Maya 없이 일정 시간이 지나면 스스로 종료한다
- **명명된 뮤텍스로 단일 인스턴스.** 플러그인을 반복 로드해도 감시자가 떼로 생기지 않는다
- **PID를 찾을 필요 없는 킬 스위치.** 명명된 이벤트 하나로 즉시 종료한다
- **자기 PID·시작 시각을 알려진 파일에 기록.** 사람이 손으로 찾을 때 헤매지 않는다

여기에 더해 **플러그인 로드 시 자가 점검** — 붙을 Maya가 없는 낡은 감시자를 발견하면 종료시킨다.

### 5.3 감시자가 죽으면 플러그인이 오판한다

플러그인 쪽에서 파이프가 끊기는 것은 *감시자*가 죽었다는 뜻이다. 극적인 결론을 내리지 않고 "진단 오프라인"으로 기록한 뒤, 재기동을 **한 번만** 시도하고 계속 진행한다.

### 5.4 강등 중 지식 DB가 갈라진다

감시자가 죽어 플러그인이 로컬 기록으로 강등되면 두 갈래가 생긴다. 플러그인의 강등 기록은 **스필 파일**로 나가고 감시자가 다음 기동 때 흡수한다. 정식 DB의 단일 쓰기자 원칙이 유지된다.

## 6. 기존 코드 정리

`Maro_DebugUtility/`는 517줄이고 실체가 있으나 세 가지를 손봐야 한다.

- **CP949 인코딩** — 플러그인에서 이미 겪고 고친 것과 같은 문제. UTF-8로 변환한다
- **`BoadMaro::dumpState(const ViewportStreamer*)` 결합** — 로거가 특정 클래스에 묶여 있다. 헤더 주석도 옮기라고 적혀 있다. 일반 상태 제공자로 분리하거나 제거한다
- **빌드 누락** — 옛 colcon 트리에 `COLCON_IGNORE`로 방치되어 새 CMake가 전혀 모른다. `src/` 아래로 정식 편입한다

`offix_Maro.h`의 주석은 이미 "Out-of-Process 디버깅 분석 시뮬레이션"이라 되어 있다. 이 설계는 방향 전환이 아니라 원래 의도의 완성이다.

## 7. 검증 — 컴퓨터를 죽이지 않는다

| 시나리오 | 방법 |
|---|---|
| 크래시 감지 | 플러그인이 `SESSION_END_CLEAN` 없이 파이프 핸들을 닫는다. 감시자 입장에서 진짜 크래시와 구분되지 않는 신호 |
| 셧다운 대비 | 명명된 이벤트로 트리거를 주입한다. `WM_QUERYENDSESSION`이 왔을 때와 같은 경로 |
| 파편 조립 | 파편 파일을 손으로 써두고 감시자를 기동해 기대한 기록이 나오는지 확인 |
| job 탈출 | 감시자의 `IsProcessInJob` 보고로 단언 |
| 좀비 없음 | 각 테스트 종료 후 감시자 프로세스가 남지 않는지 확인 |
| 강등 | 감시자를 죽인 상태에서 플러그인이 계속 동작하고 과거 지식 조회가 되는지 확인 |

선례가 있다 — 기존 `rosSimCmd.cpp`의 `-testShutdown` 플래그가 정확히 `ghost`의 두 함수를 부르고 있었다.

**새로 넣는 테스트는 전부 고의로 구현을 깨서 실패하는 것까지 확인한다.** 이 프로젝트에서 통과하던 테스트가 틀린 구현도 함께 통과시킨 경우가 일곱 번 있었고, 매번 그렇게만 잡혔다.

## 8. 향후 서브시스템과의 관계

- **`maroLidar` (S4)**: 이 생태계 위에서 진단된다. LiDAR 백그라운드 스레드의 오류도 `boad`를 거쳐 감시자로 간다
- **진단 UI (후속)**: `boad`가 이미 단일 출구이므로, 시각적 관제판은 `boad`의 소비자로 붙는다. `boad`의 계약을 바꿀 필요가 없다
