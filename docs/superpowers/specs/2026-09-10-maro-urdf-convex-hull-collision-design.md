# Maro URDF 볼록 껍질 충돌체 설계 (2026-09-10)

## 1. 배경

슬라이스 1(강체 링크 `<visual>`)과 슬라이스 2(스킨 메쉬 분할)가 링크마다
형상을 갖게 만들었다. 하지만 URDF에는 아직 `<collision>`이 없다 -- 즉 RViz
에서는 로봇이 제대로 보이지만 Gazebo에서는 모든 링크가 충돌체 없이 바닥을
통과한다.

이 스펙은 3슬라이스 중 마지막이다:

| 슬라이스 | 내용 | 상태 |
|---|---|---|
| 1 | 공유 파이프라인 + 강체 링크 `<visual>` | 완료(2026-09-07) |
| 2 | 스킨 메쉬를 skinCluster 인플루언스로 분할 | 완료(2026-09-10) |
| **3** | **볼록 껍질 `<collision>`** | **이 스펙** |

## 2. 어디에 붙는가

앞 두 슬라이스가 이미 링크별 삼각형을 손에 쥐고 있다. `<collision>`은 그
삼각형의 **정점만** 필요하다 -- 지오메트리 출처(강체/스킨)를 구분하지
않는다.

```
_writeLinkMeshes 안, 링크마다:
    triangles = (강체 또는 스킨 조각)        # 기존
    writeBinaryStl(...)  -> <link>.stl        # 기존
    hull = convexHull(삼각형의 정점들)        # 신규
    writeBinaryStl(...)  -> <link>_collision.stl
    link["collisionMesh"] = "package://<robot>/meshes/<link>_collision.stl"
```

`buildUrdfXml`이 읽는 링크 딕셔너리 필드는 **둘**이다. 껍질이 만들어지면
`collisionMesh`(경로 문자열), 만들어지지 않아 박스로 폴백하면
`collisionBox`(§4) -- 박스는 파일이 아니라 URDF 안에 크기와 중심으로 직접
들어가므로 경로 문자열로 표현할 수 없다. 둘 다 없으면 `<collision>`을 내지
않는다. 둘이 동시에 있는 경우는 만들지 않는다(껍질이 되면 박스를 계산하지
않는다).

```python
{"name": str,
 "visualMesh": str | None,
 "collisionMesh": str | None,
 "collisionBox": {"size": (sx, sy, sz), "center": (cx, cy, cz)} | None}
```

`buildUrdfXml`은 `visualMesh`와 같은 방식으로 이 둘을 `.get()`으로 읽는다 --
키가 아예 없는 기존 호출부도 그대로 동작해야 한다. 순수 함수 성격은
그대로다: 파일 쓰기도 씬 조회도 하지 않고 XML 트리만 조립한다.

**껍질 함수의 계약**: `convexHull(points) -> [((x,y,z),(x,y,z),(x,y,z)), ...]
| None`. 입력은 (x,y,z) 튜플의 시퀀스, 출력은 `writeBinaryStl`이 그대로 받는
삼각형 리스트(QuickHull의 면은 언제나 삼각형이다)이며 법선이 바깥을 향하는
와인딩이다. 껍질을 만들 수 없으면 `None` -- 호출부가 그때 박스로 간다.

파일명은 시각 메쉬와 같은 살균 결과에 `_collision`을 붙인다. 살균은
`sanitizeMeshFileName`이 이미 하고 있고, 두 파일이 같은 기반 이름을 쓰므로
충돌 회피용 일련번호도 자동으로 일치한다.

## 3. QuickHull (conflict list)

**왜 순진한 증분식으로는 안 되는가.** 점마다 현재 면 전체를 훑는 구현은
O(n x F)다. F(면 수)가 작으면 빠르지만, 볼록한 표면에서는 모든 정점이
껍질에 올라 F가 n까지 자라 이차식이 된다. 실측:

| 입력(5000점) | 껍질 정점 | 시간 |
|---|---|---|
| 요철 있는 유기적 표면 | 103 | 0.50초 |
| **원통(볼록)** | **4999** | **18.9초** |

그리고 더 큰 입력에서는 8000점 48초, 20000점 318초로 악화된다. 원통·박스·
캡슐은 로봇 파트에서 예외가 아니라 기본이므로, **최악의 경우가 곧 흔한
경우**다.

**conflict list가 고치는 것.** 각 점을 자기가 보이는 면 **하나**에만 달아
둔다. 점을 껍질에 추가할 때는 그 점이 달린 면에서 시작해 인접 면으로
넓히며 가시 영역을 찾고(flood fill), 제거되는 면들에 달려 있던 점들만 새로
만들어진 면으로 재배정한다. 점마다 전체 면을 다시 훑는 일이 없어져
평균 O(n log n)이 된다.

절차:

1. 초기 사면체를 만든다 -- 서로 다른 점, 공선 아닌 셋째 점, 공면 아닌
   넷째 점을 찾는다. 못 찾으면 §4의 폴백으로 간다.
2. 모든 면의 법선이 바깥을 향하도록 사면체 무게중심 기준으로 정렬한다.
3. 남은 점을 각각 자기가 보이는 면 하나에 배정한다(어느 면에서도 안 보이면
   내부 점이므로 버린다).
4. 점이 달린 면이 남아 있는 동안: 그 면에서 가장 먼 점을 고르고, 그
   점에서 보이는 면들을 flood fill로 모으고, 그 경계(horizon)의 각 변과
   그 점으로 새 면을 만들고, 제거된 면들의 점을 새 면으로 재배정한다.

## 4. 껍질을 만들 수 없을 때 -- AABB 박스 폴백

세 가지 경우다: 점이 4개 미만, 전부 공선, 전부 공면. **실측 확인**: 25개
공면 점과 3개 점에서 초기 사면체 구성이 실패한다.

그때는 파일을 쓰지 않고 URDF 안에 직접 박스를 낸다:

```xml
<collision>
  <origin xyz="cx cy cz" rpy="0 0 0"/>
  <geometry><box size="sx sy sz"/></geometry>
</collision>
```

`cx cy cz`는 링크 프레임 기준 AABB의 **중심**이다 -- 메쉬와 달리 원점이
영이 아니다(메쉬는 정점을 이미 링크 프레임으로 구웠지만, 박스는 원점
중심으로 정의되므로 중심을 `<origin>`으로 옮겨야 한다).

**두께가 0인 축은 1mm로 올린다.** 공면 입력이면 한 축의 범위가 정확히 0이
되는데, 크기가 0인 `<box>`는 물리 엔진이 거부하거나 정의되지 않은 동작을
한다. 1mm는 이 프로젝트가 다루는 로봇 스케일에서 무시할 수 있으면서 0이
아닌 값이다.

점이 하나도 없는 링크(지오메트리가 아예 없는 조인트)는 `<collision>`도
내지 않는다 -- `<visual>`이 없는 것과 같은 이유이며 에러가 아니다.

## 5. 알면서 받아들이는 한계

**볼록 껍질은 오목한 부분을 메운다.** L자 파트나 구부러진 팔은 껍질이
안쪽 공간을 채워 실제보다 큰 충돌체가 된다. 볼록 근사의 정의상 피할 수
없고, 해결하려면 볼록 분해(convex decomposition)라는 별개의 큰 작업이
필요하다.

`<visual>`은 실제 형상 그대로이므로 RViz에서 보이는 모양은 정확하다.
커지는 것은 충돌체뿐이다.

스킨 조각(슬라이스 2)은 이음매가 열린 껍데기지만, 볼록 껍질은 점 집합만
쓰므로 닫혀 있을 필요가 없다 -- 슬라이스 2의 §8이 이미 그렇게 적어 두었다.

## 6. 테스트 전략

| 대상 | 방식 | 배치 가능 |
|---|---|---|
| 껍질 정확성 | 큐브 8정점 -> 삼각형 12개. 내부 점을 섞어도 결과가 같다 | 예 |
| 껍질 위/안 | 모든 입력 점이 껍질 밖에 남지 않는다(각 면의 바깥쪽에 점 0개) | 예 |
| 와인딩 | 부호 있는 부피 > 0 (슬라이스 1·2가 쓴 발산정리 그대로) | 예 |
| **볼록 입력 성능** | 원통형 점 집합에서 **면 가시성 검사 횟수**가 상한 이하 | 예 |
| 폴백 3종 | 3점 / 공선 / 공면 -> `<box>`, 0 두께 축이 1mm | 예 |
| `buildUrdfXml` 분기 | `collisionMesh`면 `<mesh>`, `collisionBox`면 `<box>`, 둘 다 없으면 `<collision>` 자체가 없다 | 예 |
| 통합 | export -> `<visual>`과 `<collision>`이 둘 다 나오고 collision STL의 삼각형이 visual보다 적다 | 예 |

**성능 테스트가 시간이 아니라 연산 횟수를 세는 이유**: 벽시계 시간은
머신과 부하에 따라 흔들려서 임계값을 느슨하게 잡을 수밖에 없고, 그러면
이차식 회귀가 조용히 통과한다. 가시성 검사 횟수는 결정적이라 상한을 좁게
걸 수 있다. 이 슬라이스의 존재 이유가 그 절벽을 없애는 것이므로 그것을
직접 겨눈다.

## 7. 범위 밖

- **볼록 분해** -- 오목 파트를 여러 볼록 조각으로 나누기. §5 참고.
- **`<collision>` 전용 단순화 파라미터**(면 수 상한 등) -- 껍질을 그대로 쓴다.
- **원통·구 프리미티브 자동 인식** -- 메쉬 또는 박스로만 낸다.
- **`<inertial>`** -- 질량·관성 텐서는 이 슬라이스가 다루지 않는다.
- **numpy 도입** -- QuickHull을 제대로 구현하면 필요 없다(사용자가 명시적으로
  이 방향을 골랐다).

## 8. 전역 제약

- 빌드는 항상 `--config Release`, `ctest --test-dir out/build -C Release
  --output-on-failure`가 전부 통과해야 한다.
- `.py`만 고쳤을 때 `cmake --build`가 필요한지는 **그 테스트가 `sys.path`에
  무엇을 넣는지**로 갈린다(2026-09-10 실측, 세 번째 정정):
  - `<repo>/python`을 넣는 파일(10개 -- `test_urdf_export`, `test_publish`,
    `test_tech_diag`, `test_settings_panel` 등)만 소스를 직접 import한다
    -> 빌드 불필요.
  - 나머지 14개는 플러그인 옆 **스테이징 사본**
    (`out/build/src/maro_plugin/$<CONFIG>/`)을 import한다 -> **빌드 필수**.
  - **`sys.path.insert`가 있다고 소스가 아니다.** 인자가 `pluginDir`이면
    스테이징이다(`test_panel_commands`가 정확히 그렇다). 판단하려면
    insert의 **인자**를 봐야 한다.
  **안전한 기본값: `.py`를 고쳤으면 그냥 빌드한다.** 이 규칙은 이 리포에서
  두 번 잘못 적혔다(처음 "항상 필요", 다음 "전혀 불필요"). 파일 목록을
  외우지 말고 대상 파일의 `sys.path.insert` 인자를 직접 확인하라.
- 테스트 블록은 `tests/maya/test_urdf_export.py`의 **teardown 바로 앞**에
  넣는다. 파일 끝은 `sys.exit(0)` 뒤라 실행되지 않는다(슬라이스 2에서
  실측으로 발견 -- RED 단계가 PASS로 나와서 드러났다).
- `buildUrdfXml`은 순수 함수로 남는다.
- 새 파이썬 모듈을 만들지 않는다(전부 `maroUrdfExport.py` 안). 만들었다면
  `MARO_PLUGIN_PY_MODULES`에 반드시 추가한다.
- 새 `.py`는 `setStyleSheet()`를 호출하지 않는다.
- STL 쓰기는 기존 `writeBinaryStl`을 그대로 쓴다 -- 형식을 다시 구현하지
  않는다.
