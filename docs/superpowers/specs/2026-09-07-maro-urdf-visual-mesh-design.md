# Maro URDF 시각 메쉬 설계 (2026-09-07)

## 1. 배경

`2026-09-02-maro-urdf-export-design.md`가 만든 URDF 내보내기는 기구학만
담는다 -- 링크는 `<link name="..."/>` 하나뿐이고 형상이 전혀 없다. 그
스펙의 §5가 "시각/충돌 메쉬(`<visual>`/`<collision>`) -- §1에서 사용자가
명시적으로 다음 슬라이스로 미룸"이라고 적어 둔 그 후속 과제다.

형상이 없는 URDF는 RViz에서 좌표축만 뜨고 Gazebo에서는 링크가 충돌체
없이 바닥을 통과한다. 즉 지금의 내보내기 결과는 기구학 검증에는 쓰이지만
실제 시뮬레이션·시각화 파이프라인에는 반쪽이다.

## 2. 이 스펙의 범위: 3슬라이스 중 첫 번째

브레인스토밍에서 전체 목표(스킨 메쉬 분할 + 볼록 껍질 충돌체)를 확인한 뒤,
그것이 이 프로젝트가 평소 하나의 스펙으로 다루던 크기를 넘는다고 판단해
사용자와 함께 세 슬라이스로 나눴다:

| 슬라이스 | 내용 | 상태 |
|---|---|---|
| **1** | **공유 파이프라인 + 강체 링크 `<visual>`** | **이 스펙** |
| 2 | 스킨 메쉬를 skinCluster 인플루언스로 분할 | 별도 스펙 |
| 3 | 볼록 껍질 `<collision>` | 별도 스펙 |

셋이 독립적으로 쓸모 있다는 것이 이 분할의 근거다. 슬라이스 1만으로도
RViz에 실제 형상이 나오고, 볼록 껍질은 "어떤 점 집합이든 껍질을 만든다"는
순수 함수라 지오메트리 출처를 몰라도 된다.

## 3. 어떤 메쉬가 어느 링크에 속하는가

링크는 이미 `boundTargetPath`(축에 바인딩된 Maya 트랜스폼)로 정해져 있다
(`_buildRobotModel`). 그 트랜스폼의 **직속 셰이프 자식** 중 `mesh` 타입만
가져온다:

```python
cmds.listRelatives(linkTransform, shapes=True, fullPath=True, type="mesh")
```

**`allDescendents`를 쓰면 안 된다.** 조인트 체인에서 한 링크의 자손에는
자식 링크의 메쉬가 포함되므로, 자손 전체를 훑으면 같은 지오메트리가 두
링크에 중복으로 들어가고 부모 링크가 로봇 전체를 삼킨다. 이 함정은
`maroDagMenu._findLidarForMesh`가 `listRelatives(shapes=True)`로 직속만
보는 것과 같은 이유다.

메쉬 셰이프가 없는 링크(조인트, 로케이터)는 `<visual>` 없이 나간다 --
지금과 같은 결과이며 에러가 아니다. 삼각형이 0개인 메쉬도 같다(파일을
쓰지 않고 `<visual>`도 생략).

## 4. 좌표계와 단위

정점은 **링크 자신의 프레임**으로 구워 넣는다. 순서:

1. 링크 트랜스폼의 월드 역행렬을 정점에 곱해 링크 로컬로
2. Maya -> ROS 축 재배치 `(x, y, z) -> (x, -z, y)`
3. 씬 선형 단위 -> 미터 스케일

**축 재배치가 와인딩을 보존한다.** 그 선형변환의 행렬식은 +1이다
(X축 -90° 회전이며 반사가 아니다). 따라서 삼각형 정점 순서를 그대로 두어도
법선이 뒤집히지 않는다. 반사였다면 삼각형마다 정점 두 개를 맞바꿔야 했다 --
이 사실을 확인하지 않고 넘어가면 RViz에서 안팎이 뒤집힌 메쉬가 나온다.

**포즈 기준이 기존 관례와 일치한다.** 지금 `computeRelativeOrigin`은
내보내는 시점의 **현재 포즈**를 URDF의 영점으로 삼는다. 정점을 링크 로컬로
굽는 것은 정확히 같은 기준이므로 조인트 원점과 메쉬가 어긋나지 않는다.
(포즈 독립적인 "바인드 포즈" 기준으로 바꾸는 것은 이 스펙의 범위 밖이며,
바꾼다면 조인트 원점 쪽도 함께 바꿔야 한다.)

축 재배치는 `maroLimitCalibration.mayaDirectionToRos`가 이미 파이썬으로
하는 것과 같은 식이다. 그 전례를 따른다 -- 정점 수천 개를 `maroMayaToRos`
커맨드로 하나씩 넘기지 않는다(그 커맨드는 값 하나를 위한 것이다).

## 5. STL 쓰기

새 순수 함수 `writeBinaryStl(triangles, path)`. `triangles`는
`[((x,y,z), (x,y,z), (x,y,z)), ...]` 형태의 리스트다.

**어디에 두는가**: `python/maroUrdfExport.py` 안. 이 함수의 소비자는 URDF
내보내기 하나뿐이고, 그 파일은 지금 466줄이라 새 모듈로 쪼갤 만큼 크지
않다. 새 모듈을 만들면 `MARO_PLUGIN_PY_MODULES` 등록이 함께 필요해지는데
(§10) 그 비용을 치를 이유가 없다. 슬라이스 3(볼록 껍질)에서 지오메트리
유틸이 더 늘면 그때 함께 분리를 재검토한다.

바이너리 STL 형식:

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 80 | 헤더. `"Maro URDF export"`를 쓰고 나머지는 0으로 채운다 |
| 80 | 4 | `uint32` 삼각형 수 |
| 84 + 50k | 50 | 삼각형 k: 법선 3×`float32`, 정점 9×`float32`, `uint16` 속성 |

전부 리틀엔디언. 법선은 정점에서 계산해 채운다(대부분의 뷰어가 무시하고
다시 계산하지만, 0으로 두면 형식을 잘못 쓴 것과 구별되지 않는다).

`maroSyntheticDataPointCloud.writePly`와 같은 결이다 -- 지오메트리 파일을
Maya 익스포터에 맡기지 않고 직접 쓴다. 그래야 좌표·단위 변환을 정점에
바로 적용할 수 있고(익스포터의 단위 해석에 의존하지 않는다), 순수 함수라
배치 테스트로 왕복 검증이 된다.

## 6. 파일 배치와 URDF 참조

```
<선택한 경로>/robot.urdf
<선택한 경로>/meshes/<linkName>.stl
```

URDF는 ROS 표준 관례로 참조한다:

```xml
<link name="base">
  <visual>
    <origin xyz="0 0 0" rpy="0 0 0"/>
    <geometry>
      <mesh filename="package://robot/meshes/base.stl"/>
    </geometry>
  </visual>
</link>
```

`<robotName>`은 지금도 `.urdf` 파일명에서 오는 값을 그대로 쓴다
(`export()`의 `os.path.splitext(os.path.basename(path))[0]`).

`<origin>`이 영인 것은 정점을 이미 링크 프레임으로 구웠기 때문이다 --
변환을 URDF 쪽 `<origin>`/`<scale>`로 미루지 않는다.

**링크 이름을 그대로 파일명에 쓰지 않는다.** `_shortName()`은 DAG 경로를
`|`로만 쪼개므로 네임스페이스가 붙은 노드는 링크 이름이 `ns:cube`가 된다
(실측 확인: `_shortName`은 `:`를 건드리지 않는다). `:`는 Windows 파일명에
쓸 수 없으므로 그대로 쓰면 내보내기가 실패한다. 파일명은
`[A-Za-z0-9_-]` 이외의 문자를 `_`로 바꾼 뒤 쓰고, 그 결과가 서로 충돌하면
(`a:b`와 `a-b`가 둘 다 `a_b`가 되는 경우) 뒤에 일련번호를 붙여 유일하게
만든다. **URDF 안의 `<link name=>`은 지금 값을 그대로 둔다** -- 그건 이미
동작하는 기존 계약이고, 이번 변경이 건드릴 이유가 없다. 즉 링크 이름과
파일명은 별개이며 `<mesh filename=>`만 살균된 쪽을 가리킨다.

**`package://`의 알려진 조건**: 내보낸 디렉터리를 ROS 패키지로 등록하기
전에는(package.xml 추가 + ament 인덱스) 경로가 풀리지 않는다. 상대경로
대신 이것을 고르는 이유는 URDF 명세상 `filename`이 URI이고 상대경로 해석이
도구마다 다른 반면, `package://`는 RViz·Gazebo가 예외 없이 지원하기
때문이다. SolidWorks·Phobos 등 기존 URDF 익스포터도 같은 선택을 한다.

## 7. `buildUrdfXml` 변경

`links`의 딕셔너리에 필드 하나를 더한다:

```python
{"name": str, "visualMesh": str | None}
```

`visualMesh`가 `None`이 아니면 `<visual>` 블록을 낸다. 이 함수는 지금처럼
순수 함수로 남는다 -- 파일 쓰기도 씬 조회도 하지 않고 XML 트리만 조립한다.
STL 파일을 실제로 쓰는 것은 `_buildRobotModel`/`export` 쪽 책임이다.

기존 호출부와 테스트는 `visualMesh` 없이도 동작해야 한다(`.get("visualMesh")`
로 읽어 없으면 `None` 취급) -- 그래야 이 변경이 기존 순수 함수 테스트를
깨지 않는다.

## 8. 테스트 전략

| 대상 | 방식 | 배치 가능 |
|---|---|---|
| `writeBinaryStl` | 삼각형 -> 바이트 왕복. 헤더 80B, 개수, 좌표, 계산된 법선 검증 | 예 |
| 정점 변환 | 알려진 입력 -> 기대 출력. Y-up->Z-up, 미터 스케일, 와인딩 보존 | 예 |
| `buildUrdfXml` | `visualMesh`를 주면 `<visual>`을 내고 `None`/생략이면 안 낸다 | 예 |
| 통합 | 폴리큐브를 축에 바인딩 -> `export()` -> `<visual>` 존재 + `meshes/*.stl` 존재 + 삼각형 수 일치 + `package://` 경로 형태 | 예 |
| 메쉬 없는 링크 | 조인트만 있는 링크가 `<visual>` 없이 나간다 | 예 |
| 중복 방지 | 부모-자식 링크 체인에서 부모가 자식 메쉬를 삼키지 않는다 | 예 |
| 파일명 살균 | 네임스페이스가 붙은 링크(`ns:cube`)가 유효한 파일명으로 나가고 `<link name=>`은 원래 값을 유지한다 | 예 |

전부 배치 mayapy로 검증 가능하다 -- 이 기능에는 Qt도 뷰포트도 없다.
마지막 두 행이 §3이 경고한 두 함정을 직접 겨눈다.

## 9. 범위 밖

- **스킨 메쉬 분할** -- 슬라이스 2.
- **볼록 껍질 `<collision>`** -- 슬라이스 3. mayapy에 scipy가 없고
  (numpy 1.26.4만 있음, 실측 확인) Boost.Geometry의 `convex_hull`은 2D
  전용이라 QuickHull을 직접 구현해야 한다.
- **재질/색상** -- STL은 색을 싣지 않는다. `<material>` 방출도 이번엔 안 한다.
- **바인드 포즈 기준 내보내기** -- §4 참고. 현재 포즈 기준을 유지한다.
- **`package.xml` 생성** -- 내보내기가 ROS 패키지를 만들어 주지는 않는다.
- **메쉬 데시메이션/LOD** -- 원본 삼각형을 그대로 쓴다.
- **NURBS·서브디비전 서피스** -- `mesh` 셰이프만 본다. 다른 지오메트리
  타입은 `<visual>` 없이 나간다(에러 아님).

## 10. 전역 제약

- 빌드는 항상 `--config Release`, `ctest --test-dir out/build -C Release
  --output-on-failure`가 전부 통과해야 한다.
- 새 `.py`는 `setStyleSheet()`를 호출하지 않는다(이번엔 UI가 없지만 규율 유지).
- 좌표 변환 수식을 다시 구현하지 않는다 -- 축 재배치는
  `mayaDirectionToRos`와 같은 식을 쓰고, 그 사실을 주석으로 연결한다.
- `buildUrdfXml`은 순수 함수로 남는다(파일 I/O도 씬 조회도 하지 않는다).
- 새 파이썬 모듈이 생기면 `src/maro_plugin/CMakeLists.txt`의
  `MARO_PLUGIN_PY_MODULES` 목록에 반드시 추가한다 -- 빠뜨리면 플러그인
  옆에 스테이징되지 않아 런타임에 import가 실패한다.
