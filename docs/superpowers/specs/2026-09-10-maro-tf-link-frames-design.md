# Maro TF를 URDF 링크 프레임에 맞추는 설계 (2026-09-10)

## 1. 배경

URDF 내보내기(2026-09-02)와 라이브 `/tf` 발행(그 이전)은 서로를 모르고
각각 설계됐다. 2026-09-10에 URDF 3슬라이스(`<visual>`, 스킨 분할,
`<collision>`)가 끝나면서 둘이 처음으로 같은 로봇을 서술하게 됐고, 거기서
어긋남이 드러났다.

| | 프레임 이름 | 프레임 자세 | 구조 |
|---|---|---|---|
| URDF | 링크 = `_shortName(boundTargetPath)` | maroAxis **로케이터의 부모 트랜스폼**, 강체 | 계층, 상대 원점 |
| 런타임 `/tf` | **조인트 이름**(`jointName`) | **바인딩 타겟**의 `inclusiveMatrix()` | 평평, 절대 |

두 축이 전부 다르다. 결과적으로 URDF가 말하는 링크 프레임은 **아무도
발행하지 않고**, 런타임이 발행하는 프레임은 URDF에 **존재하지 않는다**.

`/joint_states`는 이미 맞다 -- 이름이 URDF `<joint>` 이름과 같고, 값도
`asMAngle().asRadians()` / `asMDistance().asMeters()`라 URDF limit 단위와
같다. 이 스펙은 그쪽을 건드리지 않는다.

**이건 "URDF가 고장났다"가 아니다.** `robot_state_publisher`를 띄우면
관절 구조는 동작한다. 문제는 (a) 로봇의 월드 배치를 아는 건 Maro의 TF뿐인데
rsp는 그걸 읽지 않아 로봇이 원점에 서고, (b) 두 메커니즘이 `world` 아래에
서로 만나지 않는 트리 두 개를 만든다는 것이다.

**사용자가 고른 방향**: Maro가 직접 링크 프레임을 발행한다(rsp 불필요).
프레임은 `world` 아래 **평평하게** 둔다 -- RViz의 RobotModel은 계층을
요구하지 않고 각 링크 프레임이 존재하기만 하면 되며, Maya가 이미 절대
자세를 주므로 상대 변환을 계산할 이유가 없다. 평평한 쪽이 중간 링크가
빠져도 나머지가 멀쩡하다는 이점도 있다.

## 2. 바꾸는 것

### 2-1. 프레임 이름: 조인트 → 링크

`MaroRosRuntime::drainAndPublish`의 `t.child_frame_id`를 `sample.jointName`
에서 `sample.linkName`으로 바꾼다. `AxisSample`에 `linkName` 필드가 는다.

### 2-2. 프레임 자세: 바인딩 타겟 → 로케이터의 부모 트랜스폼

**이걸 같이 안 바꾸면 이름만 맞고 메쉬가 어긋난다.** 시각/충돌 메쉬의
정점은 로케이터 부모 프레임 기준으로 구워져 있고(2026-09-07 스펙 §4의
정정), 조인트 원점과 관절 축도 같은 노드를 쓴다. 프레임만 바인딩 타겟에
세우면 두 노드의 차이만큼 통째로 어긋난다 -- 슬라이스 1이 실제로 겪은
버그(100mm)와 같은 종류다.

`MaroPump::collectSamples`는 이제 두 노드를 **둘 다** 쓴다:

| 쓰임 | 노드 |
|---|---|
| 링크 **이름** | 바인딩 타겟(`aTargetObject`의 소스) |
| 링크 **자세** | maroAxis 로케이터의 부모 트랜스폼 |

자세는 **강체로** 읽는다. 지금 코드는 `inclusiveMatrix()`를 그대로
`MTransformationMatrix`에 넣는데, 로케이터에 스케일이 걸려 있으면
`rotation()`이 오염된다. 파이썬 쪽 `_linkFrameWorldRigid`가 이미 같은
이유로 강체 경로를 쓰고 있다(슬라이스 1 최종 리뷰가 실측으로 잡은
"로케이터 스케일 오염"). 회전 성분을 정규화해 스케일/기울임을 버린다.

### 2-3. `enabled`는 `/joint_states`만 거른다

지금은 `if (!enabled) continue;`가 루프 앞머리에 있어 그 축이 TF에서도
통째로 사라진다. 그러면 URDF엔 있는 링크가 TF엔 없어 RViz에 프레임 없는
링크가 생긴다.

`enabled`를 "구동·관절값 보고를 끈다"로 해석한다. 비활성 축도 씬에서
여전히 공간을 차지하므로 **TF 프레임은 낸다**. `joints.name`/`position`
에만 넣지 않는다. `AxisSample`에 `enabled` 플래그가 는다.

### 2-4. 발행 조건

| | 필요 조건 |
|---|---|
| TF 프레임 | 바인딩이 있을 것(이름의 출처) |
| `/joint_states` 항목 | 바인딩 + `jointName` 비어 있지 않음 + `enabled` |

바인딩 없는 축은 링크 이름을 만들 수 없으므로 TF도 내지 않는다. 이름 없는
축은 프레임은 내되 관절값은 안 낸다 -- 프레임 이름이 더는 `jointName`에
의존하지 않기 때문이다.

## 3. 링크 이름 규칙을 양쪽에 고정한다

`_shortName(fullPath)`는 `fullPath.split("|")[-1]`이다. 네임스페이스는
**남는다**(`ns:cube` → `ns:cube`) -- `sanitizeMeshFileName`의 실측 주석이
이미 적어 둔 동작이며, `<link name=>`은 살균을 거치지 않는다는 것도 기존
계약이다.

C++ 등가물은 `MFnDagNode(targetPath).name()`이다. `partialPathName()`이
아니다 -- 이름이 모호할 때 그건 경로 조각을 돌려주는데, 파이썬의
`split("|")[-1]`은 언제나 노드 이름 하나만 준다.

두 구현이 갈라지면 프레임이 조용히 어긋난다. 이 리포가 Phase 2의
C++/Python UI 이름 계약에 쓴 방식대로, **양쪽을 한 테스트에 고정**한다.

## 4. 링크 이름 검증 (같이 고치는 잠재 버그 2건)

지금 URDF 내보내기는 `jointName`이 비면 실패시키지만 링크 이름은 검증하지
않는다. 둘 다 이번 변경으로 **더 나빠진다** -- 전에는 무효 URDF 하나였지만
이제는 TF 프레임까지 깨진다.

1. **바인딩 없는 축** → `<link name="">`. `check_urdf`가 거부한다.
2. **링크 이름 중복** → `<link name="cube">` 두 개. 무효 URDF이고, TF에서는
   두 발행자가 같은 프레임을 써서 화면이 떨린다. 메쉬 **파일명**은
   `usedNames`로 이미 중복을 피하지만 `<link name=>`은 그 함수를 거치지
   않는다.

둘 다 `jointName` 검증과 같은 자리에서 같은 방식으로 막는다 -- 조용히
넘어가지 않고 어느 축이 문제인지 이름을 달아 `ValueError`를 던진다.

## 5. 건드리지 않는 것

- **`/joint_states`의 이름과 단위** -- 이미 맞다(§1).
- **LiDAR `PointCloud2`의 `frame_id = "world"`** -- 히트 좌표가 실제로 월드
  좌표다. `lidar_link` 도입은 별개 작업이다.
- **URDF 파일 형식** -- 링크 이름 검증 외에는 그대로.

## 6. 테스트 전략

| 대상 | 방식 | 배치 가능 |
|---|---|---|
| 링크 이름 규칙 C++/Python 일치 | 같은 경로 문자열에 대해 두 구현이 같은 결과 | 예 |
| 프레임 자세가 로케이터 부모 기준 | 로케이터와 바인딩 타겟을 **서로 다른 자세**로 두고, TF가 로케이터 쪽과 일치 | 예(라이브 피어) |
| 스케일 오염 없음 | 로케이터에 비균등 스케일을 걸어도 회전이 안 흔들린다 | 예 |
| `enabled=false` | TF 프레임은 나오고 `/joint_states`엔 안 나온다 | 예(라이브 피어) |
| 이름 없는 축 | TF 프레임은 나오고 관절값은 안 나온다 | 예 |
| 빈 링크 이름 / 중복 링크 이름 | export가 `ValueError` | 예 |
| URDF ↔ TF 이름 집합 일치 | 같은 씬에서 export한 링크 이름 집합 == 발행된 `child_frame_id` 집합 | 예 |

마지막 항목이 이 스펙의 핵심 회귀 방어선이다. 두 파이프라인이 다시
갈라지면 그 테스트가 먼저 운다.

**픽스처 주의**: 로케이터와 바인딩 타겟을 같은 자세로 두면 2-2를 안 고쳐도
테스트가 통과한다. 반드시 **서로 다른 자세**로 둬야 한다 -- 슬라이스 2의
"원점 실린더는 아무것도 분할 안 돼서 틀린 구현이 통과한다"와 같은 함정이다.

`tests/maya/test_publish.py`는 지금 `child_frame_id == <조인트 이름>`과 그
값을 실제 ROS 피어로 검증한다. 그 테스트는 **의도적으로 다시 쓴다** --
기대 이름이 링크 이름으로 바뀌고, 기대 자세가 로케이터 부모 기준이 된다.

## 7. 범위 밖

- **계층 TF** -- 평평하게 둔다(§1).
- **`/robot_description` 발행** -- rsp가 필요 없어졌으므로 이번엔 안 낸다.
- **`robot_state_publisher` 연동** -- 같은 이유.
- **`<inertial>`, 볼록 분해, `lidar_link`** -- 각각 별개 작업.

## 8. 전역 제약

- 빌드는 항상 `--config Release`. C++를 고치므로 `cmake --build`가
  **필요하다**(파이썬만 고칠 때와 다르다).
- `ctest --test-dir out/build -C Release --output-on-failure` 전부 통과.
- `tests/maya/*.py`는 소스 `python/`을 직접 import한다 -- `.py`만 고쳤으면
  빌드가 필요 없다(2026-09-10 실측).
- 새 테스트 블록은 해당 파일의 teardown **바로 앞**에 넣는다.
- 커맨드/노드 경계의 예외 처리는 기존 `ScopedCommandContext` +
  `try/catch(std::exception)/catch(...)` 패턴을 그대로 따른다.
- 새 파이썬 모듈을 만들지 않는다.
