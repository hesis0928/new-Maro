# Maro Layer C-1 — 감시자 프로세스 골격 설계

작성일: 2026-08-19
선행: `docs/superpowers/specs/2026-08-14-maro-troubleshooting-ecosystem-design.md` §3(아키텍처), §4(계층 계약), §5(위험과 회피), §6(기존 코드 정리) — 이 문서는 그 스펙이 정의한 감시자를 실제로 만들기 위해 필요한 결정들을 채운다
선행: `docs/superpowers/plans/2026-08-16-maro-layer-b1b-journal.md` — 저널 포맷과 "프로세스별 파일" 관례를 그대로 물려받는다

## 1. 목적

원 스펙(2026-08-14) §2는 Layer C를 "감시자 프로세스, `boad`/`book`/`onfix`/`offix`/`ghost`/`OSbridge` 여섯 계층"으로 통째로 정의했다. 실제로 만들려면 프로세스 하나(하드코딩·job control·IPC·좀비 방지)와 그 위의 서로 다른 성격의 기능 넷(부스러기 집계·크래시 분석·셧다운 대응·시스템 로그)이 뒤섞여 있어, 한 플랜으로 만들면 중간에 끊길 경우 아무것도 못 쓰는 상태로 남는다.

이 문서는 그 첫 조각 **C-1: 감시자 프로세스의 골격**만 다룬다. 이 조각이 끝나면 플러그인이 자기 감시자를 띄우고, 파이프로 붙고, 정상/비정상 종료를 감시자가 구분해 안다 — 그 사실을 **가지고 무엇을 하는지는 아직 없다.** 부스러기 집계(offix)도, 셧다운 대응(ghost)도, 시스템 로그(OSbridge)도, book 정본 쓰기 이전도 이후 조각의 몫이다.

**이 조각을 먼저 자른 이유:** 프로세스 관리·job object 탈출·좀비 방지·IPC는 이 생태계에서 가장 위험하고 가장 새로운 부분이다(이 프로젝트가 지금까지 다룬 것은 전부 한 프로세스 안의 일이었다). 그 위에 기능을 쌓기 전에 인프라 자체가 살아남는지부터 확인한다.

## 2. 범위

### 포함

- 감시자 프로세스 `maro_sentinel.exe`: 기동, 명명된 파이프 서버, job object 탈출(3단계), 좀비 방지(5중), 정상 종료 신호로 크래시 판정
- 플러그인 쪽 배선: 로드 시 spawn/접속, 언로드 시 정상 종료 신호
- 새 공유 라이브러리 `maro_ipc`: 파이프 클라이언트/서버, 메시지 프레이밍, 명명된 뮤텍스 RAII 헬퍼, job 탈출 헬퍼, PID 기록 파일 헬퍼 — Maya를 모른다
- `Maro_DebugUtility/`의 개념(태그 이름, 계층 이름)만 참고하고 코드는 새로 쓴다(§6 참고 — 재사용할 실질 로직이 적다고 판단됨)

### 제외 (C-2 이후)

- **부스러기 스트림과 모듈별 3분할 파편** (onfix/offix/boad 태그별 최신값 유지, `offix` 실제 분석) — C-2
- **`ghost`의 셧다운 대응·조립** — C-3
- **`book` 정본 쓰기를 감시자로 이전**, `registerRemedy`의 스필 흡수 — C-4
- **`OSbridge`(Windows 이벤트 로그)** — C-4
- **행(hang) 감지(하트비트)** — 크래시(파이프 끊김)와는 다른 문제이고, 지금 당장 그 신호로 할 일이 없다. 기존 `MaroPump` 30Hz 타이머에 얹을 자리는 마련해 두되 배선하지 않는다

### 제외 — 명시적으로 안 하는 것

- **감시자 다중 인스턴스 공유.** Maya 프로세스 1개 : 감시자 1개로 고정한다 (§3.1의 근거)
- **book 동시 쓰기 직렬화의 실제 사용.** C-1은 book을 건드리지 않는다. 다만 §3.6이 만드는 명명된 뮤텍스 헬퍼는 C-4가 그대로 재사용할 수 있게 범용으로 만든다

## 3. 아키텍처

### 3.1 Maya 프로세스 1개 : 감시자 프로세스 1개

시스템 전역 공유 감시자가 아니라, 각 Maya 인스턴스가 자기 PID로 키를 잡은 감시자를 갖는다.

**공유안을 검토하고 기각한 이유:**
- 파이프가 다자 접속을 받아야 하고(접속마다 별도 상태 추적), 그러면 감시자가 "대화 상대 하나"가 아니라 진짜 멀티클라이언트 서버가 돼야 한다 — 가장 위험한 인프라를 검증하는 이 단계에서 위험을 오히려 키운다
- 감시자 하나가 죽으면 붙어 있던 모든 Maya의 크래시 감지가 함께 죽는다. 1:1이면 실패가 세션 하나로 격리된다 — "감시자가 없으면 진단이 나빠질 뿐, 기능이 나빠지지 않는다"는 원 스펙의 불변식과 1:1이 더 잘 맞는다
- 수명 관리가 애매해진다: 누가 띄우고 누가 끄는지 참조 카운팅이나 리더 선출이 필요해진다. 1:1이면 "내 Maya가 뜨면 내 감시자, 내 Maya가 내려가면 내 감시자도 정리"로 끝난다
- B-1b-1이 이미 "프로세스별 파일"로 저널을 구성해 뒀다(`maro_journal.<pid>.jsonl`). 감시자가 그 위에 놓이는 안전망이라면 같은 모양이어야 3단계 탈출의 최하위 단계("저널로 강등")가 자연스럽게 이어진다. 공유 감시자는 모양이 달라 이 관계가 깨진다

**공유안의 유일한 이점(book 정본 쓰기가 프로세스 하나로 저절로 직렬화됨)은 §3.6에서 명명된 뮤텍스로 동등하게 해결한다 — 프로세스 위상을 바꿀 이유가 못 된다.**

**명명 규칙 (전부 Maya PID로 키를 잡는다, B-1b-1의 `pathForProcess` 관례와 같은 이유):**

| 자원 | 이름 |
|---|---|
| 파이프 | `\\.\pipe\maro_sentinel_<PID>` |
| 단일 인스턴스 뮤텍스 | `Global\maro_sentinel_mutex_<PID>` |
| 킬 스위치 이벤트 | `Global\maro_sentinel_kill_<PID>` |
| PID·시작 시각 기록 파일 | `<book 디렉터리>/maro_sentinel.<PID>.json` |

### 3.2 크래시 신호 — 하트비트도 타임아웃 추측도 없다

원 스펙 §3.2 그대로: 정상 종료는 플러그인이 파이프를 닫기 **전에** `SESSION_END_CLEAN`을 보내고, 감시자는 그 메시지 없이 파이프가 끊기면 비정상 종료로 본다. Windows가 그 이상의 신호를 주지 않으므로 이것으로 충분하고, 임의의 타임아웃 값이 설계에 들어가지 않는다.

C-1의 메시지는 둘뿐이다: `HELLO`(접속 직후, 프레이밍이 제대로 도는지 확인), `SESSION_END_CLEAN`(정상 종료). 프레이밍은 태그가 붙은 임의 페이로드를 나중에 추가할 수 있게 설계하되(C-2의 부스러기 스트림이 그 확장이다), C-1은 그 확장을 쓰지 않는다.

### 3.3 job object 탈출 (원 스펙 §5.1, 순서는 플러그인이 지휘)

1. **플러그인**이 감시자를 `CREATE_BREAKAWAY_FROM_JOB` 플래그로 spawn한다. **감시자**가 기동 직후 `IsProcessInJob`으로 자기 상태를 확인해 파이프로 보고한다 — "빠져나왔겠지"가 아니라 "빠져나왔다"를 안다
2. 실패했거나(`CreateProcess` 자체가 거부) 감시자가 "아직 job 안"이라고 보고하면, **플러그인**이 WMI `Win32_Process::Create`로 다시 spawn한다. 이 경로로 만들어진 프로세스는 Maya의 자식이 아니라 WMI 서비스 밑에서 만들어지므로 Maya의 job과 무관하다. 같은 사용자 프로세스라 관리자 권한이 필요 없다
3. 둘 다 막히면 **플러그인**이 감시자 spawn을 포기하고 디스크 저널만 남긴다(B-1b-1의 기존 저널 그대로 — 감시자 유무와 무관하게 이미 항상 쌓이고 있다). 다음 플러그인 로드가 감시자를 다시 spawn 시도한다. **C-1은 저널을 "분석"하지 않는다**(그건 C-2의 offix 몫이다) — 이 3단계에서 C-1이 잃는 것은 "이번 세션에 감시자가 붙어 있었다"는 사실 하나뿐이고, 저널 자체의 보존과 (나중에 offix가 생기면) 그 분석 가능성은 전혀 줄지 않는다

### 3.4 좀비 방지 (원 스펙 §5.2 그대로, 5중)

- 모든 대기에 종료 이벤트 + 타임아웃을 함께 건다(`WaitForMultipleObjects`, 무기한 블로킹 없음)
- 절대 수명: 붙은 Maya의 파이프가 끊긴 뒤 일정 시간 내로 자진 종료(정상 종료 시엔 즉시, 비정상 종료 감지 후에도 처리할 게 없으면 곧 종료 — C-1은 분석을 안 하므로 사실상 파이프가 끊기면 바로 종료해도 된다. 절대 수명은 파이프가 영영 안 끊기는 이상 상황에 대한 안전망)
- 명명된 뮤텍스 단일 인스턴스: 같은 PID로 플러그인을 반복 로드해도 감시자가 떼로 안 생긴다
- 킬 스위치: 명명된 이벤트로 즉시 종료. **원 스펙(2026-08-14) §5.2는 이것을 "PID를 몰라도 되는" 단일 전역 이벤트로 적었지만, 이 문서가 §3.1에서 확정한 PID별 명명 규칙과는 안 맞는다(PID로 키를 잡은 이벤트를 쏘려면 결국 PID를 알아야 한다)** — 그래서 킬 스위치도 다른 모든 자원과 같이 `Global\maro_sentinel_kill_<PID>`로 PID별로 잡는다. "PID를 몰라도 된다"는 목표는 다른 방식으로 지킨다: PID 기록 파일이 애초에 PID로 이름 붙어 있으므로, 그 파일을 찾는 행위 자체가 이미 PID를 손에 쥐는 것이다 — 프로세스 목록을 따로 뒤져 대응시킬 필요가 없다는 뜻으로 이 목표를 재해석한다
- PID·시작 시각 기록 파일: 사람이 손으로 찾을 때 헤매지 않는다. 이 파일의 이름 자체가 위 킬 스위치 이벤트 이름을 바로 알려준다

추가로 **플러그인 로드 시 자가 점검**: PID 기록 파일을 보고 그 PID의 프로세스가 이미 죽었는데 파일만 남아 있으면(이전 세션이 감시자를 못 지우고 죽은 경우) 파일을 정리한다. 살아 있는데 자기 것이 아니면(같은 PID가 재사용된 극히 드문 경우) 킬 스위치로 정리 후 새로 spawn한다.

### 3.5 감시자가 죽으면 플러그인이 오판하지 않는다 (원 스펙 §5.3)

플러그인 쪽에서 파이프가 끊기는 것은 감시자가 죽었다는 뜻일 수도 있다. 극적인 결론을 내리지 않고 "감시자 오프라인"으로 표시한 뒤 재기동을 **한 번만** 시도하고 계속 진행한다 — 감시자 없이도 플러그인 자체 기능(진단, 저널)은 전혀 영향받지 않는다.

### 3.6 명명된 뮤텍스 헬퍼 — C-4가 재사용할 자리

§3.4의 단일 인스턴스 뮤텍스를 위해 `maro_ipc`에 RAII 래퍼(`NamedMutexGuard`: 생성자가 `CreateMutex`+`WaitForSingleObject`, 소멸자가 `ReleaseMutex`+`CloseHandle`, 타임아웃 지원)를 만든다. 범용으로 만들어 C-4(book 정본 쓰기를 감시자로 이전)가 같은 타입에 새 뮤텍스 이름(`Global\maro_book_write_mutex`류)만 붙여 프로세스 간 book 쓰기를 직렬화하게 한다 — 이것이 §3.1에서 기각한 "공유 감시자면 쓰기가 저절로 직렬화된다"는 이점을 1:1 위상에서 동등하게 얻는 방법이다. C-1은 이 헬퍼를 자기 몫(단일 인스턴스)에만 쓰고 book 관련 이름은 아직 만들지 않는다.

### 3.7 소스 구조와 빌드

| 위치 | 성격 | 책임 |
|---|---|---|
| `src/maro_ipc/` (신규) | Windows 전용, **Maya는 모른다** — `maro_diag`와 같은 자리 | 명명된 파이프 클라이언트/서버, 메시지 프레이밍(인코딩/파싱), `NamedMutexGuard`, job 탈출 헬퍼, PID 기록 파일 읽기/쓰기 |
| `src/maro_sentinel/` (신규) | 독립 실행 파일 `maro_sentinel.exe` | `maro_ipc`를 링크. 파이프 서버, job 탈출 실행, 좀비 방지 상태 머신. offix/ghost 로직 없음 |
| `src/maro_plugin/MaroPluginMain.cpp` (수정) | 기존 파일에 배선만 추가 | 로드 시 spawn/접속 + `HELLO`, 언로드 시 `SESSION_END_CLEAN` → 닫기. `JournalCloseGuard`/`MainThreadQueueGuard`와 같은 모양의 `SentinelGuard` |

`maro_ipc`가 `maro_plugin`(클라이언트 쪽 사용)과 `maro_sentinel`(서버 쪽 사용) 양쪽에 링크된다 — `maro_diag`가 이미 이 자리(Maya 모르고, 여러 타깃이 공유)에 있으므로 같은 자리에 하나 더 놓는 것뿐이다. Maya devkit 의존성은 여전히 `maro_plugin`에만 있다.

**감시자 spawn/접속 실패는 플러그인 로드를 막지 않는다.** book을 못 열 때, 저널을 못 열 때와 같은 규율이다 — 보존/관측이 안 될 뿐 진단 기능은 그대로 돈다.

## 4. 검증

| 시나리오 | 방법 |
|---|---|
| 정상 흐름 | 플러그인 로드(감시자 spawn 확인) → 언로드(`SESSION_END_CLEAN`) → 감시자가 스스로 정리되는지 확인 |
| 크래시 감지 | 파이프에 접속·`HELLO`는 보내지만 `SESSION_END_CLEAN` 없이 죽는 자식 프로세스(가짜 "크래시한 Maya") → 감시자가 비정상으로 판정하는지 확인. 감시자 입장에서 진짜 크래시와 구분되지 않는 신호(원 스펙 §7과 동일 원칙) |
| job 탈출 | 감시자의 `IsProcessInJob` 자가 점검 보고를 파이프로 받아 단언 |
| 좀비 없음 | 각 테스트 종료 후 `maro_sentinel.exe` 프로세스가 남지 않는지 확인(`Get-CimInstance Win32_Process` 조회, B-1b-1 검증과 같은 방식) |
| 감시자 오프라인 시 플러그인 정상 | 감시자 spawn을 강제로 실패시킨 채 플러그인을 로드·언로드 → 기존 진단·저널 기능이 전혀 안 죽는지 확인 |
| PID 기록 파일 자가 점검 | 죽은 프로세스의 PID 기록 파일을 미리 놔두고 플러그인을 로드 → 파일이 정리되고 새 감시자가 뜨는지 확인 |
| 순수 로직 | `maro_ipc`의 메시지 인코딩/디코딩은 실제 파이프 없이 gtest(`maro_ipc_tests`)로 |

새로 넣는 테스트는 전부 **일부러 구현을 깨서 실패하는 것까지 확인**한다 — 이 프로젝트가 반복해서 지켜온 규율이다.

## 5. C-2/C-3/C-4와의 관계

- **C-2(부스러기 스트림 + onfix/offix 3분할)**: C-1의 메시지 프레이밍을 확장해 태그 붙은 페이로드를 흘린다. 파이프도, spawn/좀비 방지 인프라도 그대로 재사용한다
- **C-3(ghost 셧다운 대응)**: `WM_QUERYENDSESSION` 트리거를 받아 C-2가 쌓아 둔 태그별 최신값을 3분할 파편으로 쓴다. 감시자 프로세스 자체의 수명 관리는 C-1 그대로
- **C-4(book 정본 쓰기 이전 + OSbridge)**: §3.6의 `NamedMutexGuard`를 book 쓰기 직렬화에 재사용. 감시자가 book의 유일한 쓰기자가 되고, 플러그인의 `registerRemedy` 스필은 감시자가 다음 접속 때 흡수한다(원 스펙 §5.4)

## 6. 기존 코드(`Maro_DebugUtility/`) 처리

참고만 하고 새로 쓴다. 파일당 평균 25줄 남짓의 선언 위주 스켈레톤(CP949 인코딩, `ViewportStreamer`와 결합)이라 재사용할 실질 로직이 적다는 판단이다(플랜 확정 전 직접 확인함). 태그 이름(`onfix`/`offix`/`boad`/`ghost`/`OSbridge`)과 계층 개념은 그대로 가져오되 구현은 이 프로젝트의 현재 관례(UTF-8, `maro_diag`/`maro_ipc`의 네이밍, gtest 커버리지)로 새로 쓴다. `Maro_DebugUtility/`는 손대지 않고 그대로 둔다 — C-1~C-4가 끝나면 완전히 대체되는 죽은 코드가 되지만, 실제로 지우는 것은 이 작업의 범위가 아니다(위험 없는 별개의 정리 작업).
