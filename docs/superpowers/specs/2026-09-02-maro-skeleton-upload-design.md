# Maro 스켈레톤 업로드/추출 설계

## 1. 배경

원 로드맵(`2026-08-24-maro-main-ui-phase0-1-design.md:68`)이 "Phase 4 — 업로드 +
스켈레톤 추출/생성(skinCluster 인플루언스 추출, 없으면 바운딩박스 중심에 루트
조인트 1개만 생성 — 자동 리깅 아님)"이라는 한 줄 스케치만 남겨 뒀다. 그 이후
이 프로젝트는 축/capability 편집을 네이티브 마킹메뉴(`dagMenuProc` 체이닝) +
SONE(싱글 오브젝트 노드 에디터)/ONE(오브젝트 노드 에디터) 조합으로 완전히
다시 설계했다. 이 스펙은 그 한 줄 스케치를 지금의 MaroUI 구조에 맞게
브레인스토밍으로 재구성한 것이다.

핵심 재확인 사항: 스켈레톤 추출은 마킹메뉴 기반 축 생성 워크플로를
**대체하지 않는다**. 추출/생성이 만드는 것은 어디까지나 Maya `joint`
노드들이고, 그 조인트에 `maroAxis`를 부여하는 것은 여전히 사용자가 각
조인트를 우클릭해 기존 "Maro node editor" 마킹메뉴로 하나씩 하는 일이다.
이 기능은 "조인트 계층을 준비해 주는 것"까지만 책임진다 — 자동 리깅이 아니다.

## 2. 진입점

기존 "Maro" 최상위 Maya 메뉴(`maroBuildMenu`가 만드는 메뉴)에 새 항목
**"Skeleton Upload..."**를 추가한다. 클릭하면 `python/maroSkeletonUpload.py`의
`show()`가 독립 최상위 QDialog를 연다 — SONE/`maroLidarPanel`과 같은 패턴
(모덜리스, `setStyleSheet()` 미사용, 모든 이벤트 핸들러가 예외를 삼킴,
`_OPEN_DIALOG` 싱글톤으로 재오픈 시 기존 창을 앞으로).

MaroUI 자체의 기존 레이아웃(듀얼 뷰포트 + Tech Diag 사이드패널 + ONE 그리드)은
전혀 건드리지 않는다 — 새 버튼/패널을 그 안에 끼워 넣지 않는다. 이 기능은
"설정 시점에 한 번 쓰는" 성격이라 항상 떠 있는 창보다 별도 다이얼로그가 더
어울린다는 것이 이번 브레인스토밍의 결론이다.

## 3. 다이얼로그 구성

버튼 두 개로 시작한다:

- **"파일에서 임포트"** — 클릭하면 Maya 자신의 네이티브 파일 임포트를 그대로
  호출한다(`mel.eval('FileImport')` 또는 동등한 커맨드). 드롭 이벤트를 직접
  가로채는 새 Qt 코드는 만들지 않는다 — MaroUI의 두 뷰포트(Maya/ROS)는 이미
  진짜 네이티브 `modelPanel`이므로 Maya 자신의 파일 드래그&드롭이 그 위에서
  이미 동작한다는 것이 이번 브레인스토밍의 전제다. **이 전제 자체는 인터랙티브
  Maya에서 실측 확인된 적 없다** — 계획 단계에서 명시적인 검증 항목으로
  남긴다(§7 참고).
- **"현재 선택에서 추출"** — 클릭 시점의 Maya 선택을 그대로 대상으로 쓴다.

## 4. 임포트 완료 감지

Maya의 `OpenMaya.MSceneMessage.addCallback(kAfterImport, ...)`을 쓰되, **이
다이얼로그가 열려 있는 동안만** 등록하고 닫히면(`closeEvent`) 즉시 해제한다.
전역으로 항상 걸어 두면 이 기능과 무관한 임포트(다른 목적의 File > Import)에도
반응해 버리기 때문이다 — 다이얼로그의 열림/닫힘이 자연스러운 스코프 경계다.

이 콜백에는 "무엇이 임포트됐는지"를 직접 알려주는 인자가 없으므로, 임포트
직전/직후의 `cmds.ls(assemblies=True)`(최상위 오브젝트 목록)를 비교하는 diff
방식으로 새로 생긴 최상위 오브젝트를 찾는다.

## 5. 추출 로직

`extractSkeleton(mesh)` — 대상은 메쉬 셰이프를 가진 오브젝트 하나여야 한다.

1. `cmds.listHistory(mesh)`에서 `skinCluster` 타입 노드를 찾는다(여러 개
   걸리면 첫 번째만 쓴다 — 실무에서 메쉬 하나가 활성 skinCluster를 둘 이상
   갖는 경우는 사실상 없어 과설계하지 않는다).
2. **skinCluster가 있으면**: `cmds.skinCluster(scNode, query=True,
   influence=True)`로 인플루언스 조인트 목록을 얻어 그대로
   `cmds.select(...)`한다. **새 노드는 전혀 만들지 않는다** — 인플루언스
   조인트는 이미 존재하는 진짜 `joint` 노드이므로, 이 기능이 하는 일은
   "찾아서 선택해 주는 것"이 전부다.
3. **skinCluster가 없으면**: `cmds.exactWorldBoundingBox(mesh)`의 중심에 새
   `joint` 노드 1개를 생성한다(이름: `<메쉬이름>_root`). 그 메쉬의 자식으로
   부모를 붙인 뒤(LiDAR placeholder와 같은 이유 — 소속이 분명해지고 메쉬 삭제
   시 함께 정리됨) 선택 상태로 만든다.
4. 그 다음은 이 기능의 책임 밖이다 — 선택된 조인트(들)를 사용자가 각각
   우클릭해 마킹메뉴로 `maroAxis`를 부여한다.

## 6. 오류/예외 처리

- **"현재 선택에서 추출" 클릭 시 선택이 메쉬 하나가 아님**(0개, 여러 개, 또는
  메쉬가 아닌 오브젝트) — "정확히 메쉬 하나를 선택하세요" 경고 후 중단
  (`maroLidarPanel`의 "select a mesh to add as a LiDAR target first"와 같은
  스타일).
- **skinCluster는 있지만 인플루언스가 0개인 퇴화 케이스** — "no skinCluster"
  경로로 조용히 폴백하지 않는다. "skinCluster는 있지만 인플루언스를 찾을 수
  없습니다"로 별도 경고하고 중단한다 — 씬이 실제로 깨진 상태를 감춘 채 엉뚱한
  루트 조인트를 만들어 버리면 안 되기 때문이다.
- **임포트 결과가 여러 최상위 오브젝트인 경우**(FBX가 계층 전체를 들고 옴) —
  새로 생긴 서브트리 전체(`cmds.listRelatives(newAssemblies, allDescendents=True,
  type="mesh")`)에서 첫 번째로 발견되는 메쉬 셰이프를 대상으로 추출한다.
  메쉬가 하나도 없으면 "임포트한 파일에 메쉬가 없습니다" 경고.
- **바운딩박스가 퇴화된 메쉬**(면적/부피 0 등)에서 루트 조인트 생성 — 특별
  처리 없음, 계산된 좌표를 그대로 쓴다(LiDAR placeholder가 점형 오브젝트를
  다루는 것과 같은 태도 — 워킹 스켈레톤 규모에서는 받아들여지는 동작).

## 7. 테스트 / 수동 체크리스트

- `extractSkeleton()`의 skinCluster 유무 두 경로, 인플루언스 0개 퇴화
  케이스, 다중 selection 거부는 모두 mayapy 배치로 테스트 가능하다(순수하게
  `cmds` 조회/조작만 쓰고 Qt를 만들지 않는다).
- 파일 임포트 자체(`FileImport` 호출), 다이얼로그 열림/닫힘에 따른 콜백
  등록/해제, 그리고 **가장 중요하게 — MaroUI 뷰포트에 실제로 파일을 드래그하면
  Maya의 네이티브 임포트가 정말로 동작하는지**는 배치 mayapy로 검증
  불가능하다 — `docs/maro-main-ui-manual-checklist.md`에 새 절을 추가해
  대화형 Maya에서 검증한다. 이 마지막 항목이 이 기능 전체의 진짜 위험
  가정이므로 체크리스트에서 go/no-go로 표시한다.

## 8. 전역 제약

- 이 기능은 `maroAxis`/`maroLidar`류의 새 커스텀 노드 타입을 전혀 추가하지
  않는다 — 순수 Python + 표준 Maya `joint`/`skinCluster` 커맨드로 구성된다.
  새 C++ 코드가 필요 없다.
- MaroUI의 기존 레이아웃(듀얼 뷰포트, Tech Diag 사이드패널, ONE 그리드)을
  건드리지 않는다.
- `kAfterImport` 콜백은 다이얼로그가 열려 있는 동안만 살아 있어야 하고,
  플러그인 언로드 시(또는 다이얼로그가 닫히지 않은 채 언로드되는 경우)
  반드시 해제되어야 한다 — 이 프로젝트가 반복해서 잡아 온 "주인 없는 콜백"
  결함 유형과 같은 카테고리다.
- 새 Qt 다이얼로그는 `setStyleSheet()`를 호출하지 않고, 모든 이벤트 핸들러가
  예외를 삼킨다(이 코드베이스의 기존 전역 규율).
