#### `__file__` 단언

**직관:** 테스트가 import한 모듈이 **스테이징된 사본**인지 확인하는 단언. "런타임에 실제로 실행되는 것이 그것이다"를 고정한다.

**동작:** Maya 테스트는 `pluginDir = os.path.dirname(plugin); sys.path.insert(0, pluginDir)`로 `.mll` 옆의 `.py` 사본을 import한다. 소스 트리의 `python/`이 아니라 빌드가 복사한 사본이 실제로 로드되는 것이므로, `__file__`이 스테이징 경로인지 단언해 "소스는 고쳤는데 사본은 옛 것"인 상황을 잡는다. 같은 규율이 `test_ros_proxy_sync`·`test_main_window`·`test_dag_menu`·`test_panel_commands`에 있다.

**예시:**
```python
import maroMainWindow
assert os.path.dirname(maroMainWindow.__file__) == pluginDir, maroMainWindow.__file__
```

**관련 코드:**
- `tests/maya/test_main_window.py` — `__file__` 단언
- `src/maro_plugin/CMakeLists.txt:110-130` — `.py` 스테이징

**증거:**
- §8.3, §8.3.0

**함정:** 개발자가 소스 트리를 `sys.path`에 넣어 두면 그쪽이 먼저 잡혀 스테이징 사본이 검증되지 않는다. 단언이 그 상황을 드러낸다.

**교훈:** "무엇이 실행되는가"를 테스트가 스스로 확인한다. 빌드 파이프라인이 있는 프로젝트에서는 필수다.

#### 스텁 교체(`openLidarPanel`, 렌더, 원본 `dagMenuProc`)

**직관:** 배치 모드에서 부를 수 없는 함수(모달 창·렌더·MEL 원본)를 기록용 스텁으로 갈아 끼워 호출 계약만 검증하는 기법.


**교훈:** UI 경계의 계약은 "무엇을 불렀는가"로 검증할 수 있다. 실제 표시는 사람이 본다.

#### 호출 순서·인자 단언

**직관:** 스텁이 기록한 호출 목록을 순서까지 포함해 단언하는 방식. "불렸다"가 아니라 "이 순서로 이 인자로 불렸다"를 고정한다.


#### 미끼 자세(decoy)

**직관:** "값의 출처가 틀리면 실패하도록" 일부러 다른 값을 가진 노드를 옆에 두는 기법. 바인딩 타겟과 로케이터 부모가 다른 자세를 갖게 해 둔다.

**동작:** `test_publish.py`는 `/tf`의 자세가 **로케이터의 부모 transform**에서 와야 한다는 계약(§2-2)을 검증하려고, 바인딩 타겟에 다른 자세를 준다. 구현이 잘못된 노드에서 자세를 읽으면 미끼 값이 나와 단언이 깨진다. 같은 이유로 세 성분이 모두 다르고 0이 아닌 값, 손으로 유도한 쿼터니언을 쓴다.

**예시:**
```
로케이터 부모: rotate (10, 20, 30)   ← 기대 출처
바인딩 타겟:   rotate (40, 50, 60)   ← 미끼
단언: /tf rotation == quat(10,20,30)
```

**관련 코드:**
- `tests/maya/test_publish.py:94-140` — 미끼 배치와 단언
- `src/maro_plugin/MaroPump.cpp:225-240` — 실제 자세 출처

**증거:**
- §8.3, §8.3.2

**함정:** 두 노드의 자세를 같게 두면(흔한 픽스처) 어느 쪽에서 읽어도 통과한다 — 대표적인 픽스처 함정이다.

**교훈:** "어디서 왔는가"를 검증하려면 출처마다 값을 다르게 만든다. 같은 값은 출처를 구별하지 못한다.

#### 세 성분 모두 다르고 0 아님

**직관:** 벡터·쿼터니언 테스트 입력을 고를 때의 규칙. 성분이 같거나 0이면 축 교환·부호 오류가 숨는다.

**동작:** `test_publish.py`의 자세 값은 세 성분이 모두 다르고 어느 것도 0이 아니다. 그래야 (x,y,z)→(x,z,y) 같은 교환이나 부호 오류가 결과를 바꾼다. 같은 규칙이 `test_convert.cpp`의 "z=0이면 −0과 0을 구별 못 한다"와 맞닿아 있다.

**예시:**
```
나쁨: (1, 1, 1)   → 어떤 치환도 같은 값
나쁨: (1, 0, 0)   → y/z 오류가 안 보임
좋음: (0.3, -0.7, 1.2)
```

**관련 코드:**
- `tests/maya/test_publish.py:94-140` — 값 선택
- `tests/transform/test_convert.cpp:64-88` — 같은 규칙

**증거:**
- §8.3, §8.3.2

**함정:** 읽기 쉬운 값(0, 1, 같은 수)이 가장 약한 입력이다. 편의가 검증력을 깎는다.

**교훈:** 테스트 입력은 "구별력"으로 고른다. 사람이 읽기 좋은 값은 대개 구별력이 낮다.

#### 손으로 유도한 쿼터니언

**직관:** 기대값을 코드로 계산하지 않고 손으로 유도해 상수로 박는 방식. 구현과 기대값이 같은 함수를 쓰면 검증이 순환한다.

**동작:** `test_publish.py`는 기대 쿼터니언을 손으로 계산해 넣는다 — 구현의 `jointToMayaRotation`을 불러 기대값을 만들면 그 함수가 틀려도 통과하기 때문이다. 같은 정신이 URDF 테스트의 독립 회전행렬 오라클(`_rotX/_rotY/_rotZ`·`_matmul`)이다. 즉 "다른 방법으로 계산한 값"이 기대값이어야 한다.

**예시:**
```python
# 구현을 부르지 않고 손으로: 60° about Z → (0, 0, sin30°, cos30°)
expected = (0.0, 0.0, 0.5, 0.8660254)
```

- `tests/maya/test_urdf_export.py:165-215` — 독립 오라클

**증거:**
- §8.3, §8.3.2

**함정:** 기대값을 구현으로 만들면 테스트가 "구현은 구현과 같다"를 확인한다. 가장 흔한 순환 검증이다.

**교훈:** 기대값은 구현과 독립적인 경로로 구한다. 손 계산, 독립 구현, 외부 도구 중 하나다.

#### `PID_MARKER`

**직관:** 자식 프로세스가 자기 PID를 부모에게 알리는 표식 문자열. 로그에서 그 줄을 찾아 PID를 얻는다.

**예시:**
```python
sys.stdout.write("PID_MARKER %d\n" % os.getpid()); sys.stdout.flush()
```

#### `os._exit` 전 flush

**직관:** `os._exit`는 stdio 버퍼를 비우지 않고 즉시 죽는다. 표식이나 로그를 남기려면 그 전에 직접 flush해야 한다.

**동작:** 크래시 세션은 `os._exit(3)`으로 `uninitializePlugin`(=SESSION_END_CLEAN) 없이 끊어 진짜 크래시를 흉내 낸다. 감시자 입장에서 구분되지 않으면서 컴퓨터를 죽이지 않고 만들 수 있는 유일한 방법이다. 표식은 그 직전에 `write` + `flush`로 내보낸다.

**예시:**
```python
sys.stdout.write("PID_MARKER %d\n" % os.getpid())
sys.stdout.flush()      # os._exit는 버퍼를 버린다
os._exit(3)
```

**증거:**

**함정:** `print`만 쓰면 파이프 버퍼링(비대화형 실행)에서 통째로 사라진다. 대화형에서는 보이므로 더 헷갈린다.

**교훈:** 비정상 종료를 흉내 낼 때는 "남겨야 할 것"을 먼저 확실히 내보낸다.

#### 분할 불변식 N = A + B

**직관:** 스킨 메쉬를 두 링크로 나눌 때 삼각형 총수가 보존되는지 보는 단언. 중복이나 누락을 한 줄로 잡는다.

**동작:** `test_urdf_export.py`는 분할 전 삼각형 수 N과 분할 후 두 조각 A·B에 대해 `N == A + B`를 단언한다. 같은 삼각형이 두 링크에 들어가면 합이 커지고, 어느 링크에도 안 들어가면 작아진다. 동점 처리(1:1:1)를 "개별 가중치가 가장 큰 정점의 링크"로 정한 것도 정점 순서 의존을 배제하기 위한 결정이다.

**예시:**
```python
assert len(partA) + len(partB) == len(allTriangles)
```

#### 부호 부피(외향 법선)

**직관:** 닫힌 메쉬의 부호 있는 부피를 계산해 양수인지 보는 단언. 와인딩이 뒤집히면 음수가 되므로 법선 방향을 한 값으로 검증한다.

**동작:** 발산정리로 `V = 1/6 · Σ v0·(v1×v2)`를 계산한다. 볼록 껍질 결과와 STL 출력에 적용해 "메쉬가 안팎이 뒤집히지 않았다"를 고정하며, 실패 메시지는 "exported triangle winding is inverted — the mesh would render inside-out"이다.

**예시:**
```python
V = sum(dot(v0, cross(v1, v2)) for v0, v1, v2 in tris) / 6.0
assert V > 0, "winding inverted"
```

**증거:**

**함정:** 열린 메쉬(닫히지 않은 표면)에는 이 공식이 의미가 없다. 껍질처럼 닫힌 것에만 쓴다.

#### visibility 검사 수 상한

**직관:** QuickHull 성능을 벽시계가 아니라 "가시성 검사 호출 횟수"로 단언하는 방식. 머신 속도와 무관한 회귀 그물이다.

**동작:** `convexHull(points, stats)`가 `stats["visibilityChecks"]`를 세고, 테스트가 2000점 볼록 입력에서 200,000 미만임을 단언한다. 순진한 증분식은 O(n²)라 이 상한을 크게 넘는다. 느슨한 시간 임계값은 이차식 회귀를 조용히 통과시키므로(F-217) 이 방식이 채택됐다.

**예시:**
```python
_hullStats = {"visibilityChecks": 0}
convexHull(points2000, _hullStats)
assert _hullStats["visibilityChecks"] < 200000, _hullStats["visibilityChecks"]
```

**관련 코드:**

- `python/maroUrdfExport.py:1108-1112` — 카운터

**증거:**
- §8.3, §8.3.6, §7.14

**함정:** 상한이 너무 헐거우면 O(n²)도 통과한다. 올바른 구현의 실측값에 2~3배를 곱해 잡는다.

**교훈:** 알고리즘 복잡도는 연산 횟수로 테스트한다. 시간은 환경의 함수다.

#### 변이 검증(mutation verification)

**직관:** 구현을 **일부러 깨뜨려** 테스트가 실패하는지 확인하는 단계. 테스트의 힘은 "틀린 구현을 거부하는가"로만 측정된다.

**동작:** 플랜의 모든 새 테스트에 이 스텝이 붙는다. 변이의 예 — 부호 뒤집기, `asin`↔`atan2` 치환, `break` 제거, 상수 변경, 조건 반전. 근거는 반복된 사고다: "통과하던 테스트가 틀린 구현도 함께 통과시킨 경우"가 Layer A 시점에 일곱 번 있었다(F-195). 중요한 조건 — **실패하지 않으면 되돌리기 전에 테스트를 고친다**. 실패를 확인하지 못한 변이는 아무것도 증명하지 못한다.

**예시:**
```
1. 구현에서 (x,-z,y) → (x,z,y)로 바꾼다
2. 테스트 실행 → 실패해야 한다
3. 실패하지 않으면 테스트를 강화한다(되돌리기 전에)
```

#### `sys.exit(0)` 뒤 테스트 블록

**직관:** 스크립트 끝의 `sys.exit(0)` 뒤에 테스트를 추가하면 그 코드는 실행되지 않는다. "통과했다"가 "실행조차 안 됐다"였던 함정.

**동작:** §9.3의 "테스트 코드 삽입 위치" 교훈이다. 오케스트레이터형 테스트는 `main` 끝에서 `sys.exit(0)`으로 종료 코드를 확정하므로, 파일 끝에 블록을 붙이면 죽은 코드가 된다. 앞쪽에 넣으면 아직 정의되지 않은 이름을 참조해 `NameError`다. 규칙은 "헬퍼는 위, 실행 블록은 `main` 안, exit 앞".

**예시:**
```python
    run_as_session(label)
    sys.exit(0)
# ↓ 여기에 쓴 테스트는 절대 실행되지 않는다
assert something
```

**함정:** 실행되지 않는 테스트는 항상 초록이라 가장 늦게 발견된다. 변이 검증이 이것도 잡는다.

**교훈:** 새 테스트는 한 번 실패시켜 본다. 실행 여부를 확인하는 가장 싼 방법이다.

#### 토러스 픽스처(800→436)

**직관:** 볼록 껍질 테스트의 입력을 볼록체에서 **토러스**(오목)로 바꾼 정정. 볼록 입력으로는 "껍질이 더 작다"를 증명할 수 없기 때문이다.

**예시:**
```
볼록 입력 1000점 → 껍질 1000점   (구별력 없음)

```

#### 픽스처 함정(fixture trap)

**직관:** 틀린 구현도 통과시키는 테스트 데이터. 이 프로젝트가 유형학으로 정리해 둔 목록이 있다.

**동작:** 유형은 — (1) **대칭**: Y=0 큐브는 `yCam` 부호를 검증 못 함, (2) **일치**: 두 프레임이 같은 리그는 "어느 프레임"을 못 가림, (3) **지배**: 원점 실린더는 한 조인트가 전부 지배해 분할 로직을 안 탐, (4) **볼록**: 껍질이 입력과 같아 압축을 증명 못 함, (5) **정렬**: 순번 오름차순만 주면 순서 무관성을 못 봄, (6) **단일**: 파일당 세션 하나면 회전의 mtime 문제를 못 드러냄.

**예시:**
```
Y=0 큐브        → yCam 부호 오류 통과
두 프레임 일치   → 출처 오류 통과
원점 실린더     → 분할 로직 미실행
볼록 입력       → 껍질 압축 미검증
```

**함정:** 픽스처 함정은 테스트가 **통과할 때** 생긴다. 실패는 눈에 띄지만 약한 통과는 안 띈다.

- `tools/crashtriage/symbolize.py:40-47` — 베이스로 RVA 계산

**증거:**
- §9.5

**함정:** 폴트 모듈이 시스템 DLL이면 "OS 버그"로 결론 내기 쉽다. 거의 항상 우리가 넘긴 데이터가 원인이다.

**교훈:** 덤프 분석은 모듈 판별에서 시작한다. 그 한 줄이 이후 조사 전략을 가른다.

#### 읽기·쓰기 대상

**직관:** 액세스 위반 예외의 보조 정보 — 읽기였는지 쓰기였는지와 접근하려던 주소. 코드값보다 많은 것을 알려 준다.

**동작:** `ExceptionInformation[0]`이 0이면 읽기, 1이면 쓰기, 8이면 DEP 위반이고 `[1]`이 대상 주소다. `parse_minidump.py`가 이 둘을 함께 출력한다. 09-06 사례에서 "쓰기 대상 모듈이 매번 다름"이 힙 손상의 결정적 단서였다 — 읽기/쓰기 구분이 없었다면 그 패턴을 못 봤다.

**예시:**
```
ExceptionInformation = [1, 0x000001F4A2B30000]
→ 쓰기, 그 주소. 주소가 매번 다르면 힙 손상 의심
```

**관련 코드:**
- `tools/crashtriage/parse_minidump.py:30-60` — 보조 정보 출력

**증거:**
- §9.5

**함정:** 읽기 오류와 쓰기 오류는 조사 범위가 다르다. 읽기는 초기화·수명, 쓰기는 버퍼·소유권을 먼저 본다.

**교훈:** 예외 정보의 모든 필드를 출력한다. 쓰지 않을 정보는 없다.

#### 가난한 자의 스택(stack scan)

**직관:** 스택 메모리를 훑어 코드 주소처럼 보이는 값을 모으는 방식. 진짜 스택 언와인딩이 아니므로 **근거로 쓸 수 없다**.

**동작:** 프레임 포인터나 언와인드 정보가 없을 때 디버거가 쓰는 폴백이다. 스택에 남은 옛 반환 주소·우연히 코드 범위에 드는 값이 섞여 실제 호출 경로가 아닌 목록을 만든다. 그래서 이 프로젝트는 스택 스캔 결과를 "참고"로만 보고, 판정은 심볼화된 실제 프레임(`boost::stacktrace`)이나 미니덤프의 컨텍스트로 한다.

**예시:**
```
스택 스캔 결과: A(), B(), C(), D()   ← 일부는 옛 프레임의 잔재
실제 호출 경로: A() → D()
```

**관련 코드:**
- `tools/crashtriage/symbolize.py:60-75` — 명시적 주소 심볼화
- `src/maro_plugin/MaroStackTrace.cpp:80-95` — 진짜 언와인딩

**증거:**
- §9.5

**함정:** 스택 스캔이 그럴듯한 함수 이름을 늘어놓으면 그것을 호출 경로로 믿게 된다. 거짓 단서가 조사를 오래 끈다.

**교훈:** 추정과 관측을 구분한다. 스택 스캔은 추정이다.

#### RVA(Relative Virtual Address)

**직관:** 모듈 베이스로부터의 상대 주소. 심볼화의 입력 단위이며, 모듈이 로드되는 주소가 매번 달라도 RVA는 같다.

**동작:** 크래시 덤프의 폴트 주소(절대)에서 `maro.mll` 베이스를 빼면 RVA가 된다. `symbolize.py`가 `SymLoadModuleEx`에 베이스를 넘기고 절대 주소를 주면 dbghelp가 내부적으로 RVA를 써서 PDB를 조회한다. ASLR 때문에 절대 주소는 실행마다 다르지만 RVA는 빌드에 고정된다.

**예시:**
```
폴트 주소 0x7FFA_0001_2345
maro.mll 베이스 0x7FFA_0000_0000
RVA = 0x12345  → PDB 조회
```

**관련 코드:**
- `tools/crashtriage/parse_minidump.py:30-60` — 베이스 추출
- `tools/crashtriage/symbolize.py:40-47` — 모듈 로드

**증거:**
- §9.5

**함정:** 다른 빌드의 PDB로 조회하면 같은 RVA가 다른 함수를 가리킨다. 빌드 짝이 맞는지가 전제다.

**교훈:** 주소는 상대화해야 의미를 갖는다. ASLR 환경에서 절대 주소는 그 실행에서만 유효하다.

#### 모듈 베이스

**직관:** 모듈이 로드된 시작 주소. RVA 계산의 기준이며 덤프의 ModuleList에서 읽는다.

**동작:** `parse_minidump.py`가 ModuleList 스트림에서 `maro.mll`의 베이스와 크기를 뽑는다. 크기는 "덤프의 모듈이 현재 빌드와 같은가"를 판단하는 데 쓴다 — 크기가 다르면 다른 빌드이므로 심볼화 결과를 믿으면 안 된다. `symbolize.py`는 이 베이스를 `SymLoadModuleEx`에 넘긴다.

**예시:**
```
ModuleList: maro.mll base=0x7FFA00000000 size=0x2A0000
현재 빌드 maro.mll 크기 != 0x2A0000 → 심볼화 결과 신뢰 불가
```

**관련 코드:**
- `tools/crashtriage/parse_minidump.py:30-60` — 베이스·크기
- `tools/crashtriage/symbolize.py:40-47` — 로드

**증거:**
- §9.5

**함정:** 크기 비교를 건너뛰면 "심볼화는 됐는데 함수가 이상한" 상태가 된다. 조용한 오답이다.

**교훈:** 심볼화 전에 "같은 바이너리인가"를 확인한다. 크기가 가장 싼 지문이다.

#### `maro.pdb`

**직관:** 컴파일러가 만드는 디버그 심볼 파일. 함수명과 소스 줄 정보가 여기 있고, 없으면 주소가 주소로만 남는다.

**동작:** Release 빌드에도 `/DEBUG`를 걸어 PDB를 만든다(ASan 블록에서도 명시). `symbolize.py`가 `SymLoadModuleEx`로 `.mll`을 로드하면 dbghelp가 같은 폴더나 심볼 경로에서 PDB를 찾는다. PDB는 빌드마다 달라지므로 크래시 덤프와 짝을 맞춰 보관해야 한다.

**예시:**
```
out/build/Release/maro.mll
out/build/Release/maro.pdb   ← 짝. 다시 빌드하면 달라진다
```

**관련 코드:**
- `CMakeLists.txt:45-60` — `/DEBUG` 보장
- `tools/crashtriage/symbolize.py:40-56` — 심볼 로드·조회

**증거:**
- §9.5

**함정:** Release 빌드에서 PDB 생성을 끄면 사용자 크래시를 분석할 수 없다. 배포하지 않더라도 보관한다.

**교훈:** 심볼 파일은 빌드 산출물의 일부다. 버전별로 보관해야 뒤늦은 덤프를 읽을 수 있다.

#### 힙 손상(heap corruption)

**직관:** 잘못된 쓰기가 힙 메타데이터를 망가뜨려, 한참 뒤 무관한 곳에서 터지는 오류. 크래시 지점과 버그 지점이 다르다.

**동작:** 09-06 사례의 원인은 `MFnPointArrayData::array()`가 돌려주는 **내부 버퍼 참조**를 멤버로 들고 있던 것이었다 — 같은 스코프에서 즉시 소비하는 `boundingBox()`는 멀쩡했지만 드로우 경로는 나중에 죽은 참조를 썼다. 증상은 `createNode` 단독 크래시, ntdll 폴트, 쓰기 대상 모듈 가변이었다. 해결은 `copyTo()`로 복사해 저장.

**예시:**
```cpp
// 위험: 내부 버퍼 참조 보관
const MPointArray& pts = fnData.array();      // 함수가 끝나면 무효
// 안전: 복사
MPointArray pts; fnData.copyTo(pts);
```

**관련 코드:**
- `src/maro_plugin/MaroPointCloudNode.cpp:241-390` — 복사 저장
- `tools/crashtriage/parse_minidump.py:30-60` — 증상 관측

**증거:**
- §9.5, §10.5
- F-023

**함정:** 재현이 확률적이고 증상이 매번 달라 "환경 문제"로 오해된다. 증상의 가변성 자체가 분류 단서다.

**교훈:** 참조를 돌려주는 API는 수명을 문서에서 확인한다. 보관해야 하면 복사한다.

#### "크래시 지점≠버그 지점"

**직관:** 힙 손상·UAF 같은 메모리 오류의 기본 성질. 터진 곳을 파면 시간을 잃는다는 경고다.

**동작:** 이 문구가 진단 절차의 분기점이다 — 폴트 모듈이 할당자 내부이거나 쓰기 대상이 매번 다르면 스택 추적이 아니라 수명 검토로 전환한다. 09-06→09-07 조사가 정확히 그 경로를 따랐다. ASan 빌드가 그 전환의 도구이고, 실패하면 최근 변경된 수명 코드를 리뷰한다.

**예시:**
```
증상: createNode에서 크래시
조사: createNode 코드 정독 → 헛수고
전환: ntdll 폴트 + 대상 가변 → 힙 손상 → 수명 검토 → array() 참조 발견
```

**관련 코드:**
- `src/maro_plugin/MaroPointCloudNode.cpp:241-390` — 실제 원인
- `docs/maro-main-ui-manual-checklist.md` — 조사 경위

**증거:**
- §9.5, §9.4
- F-023

**함정:** 스택 트레이스가 그럴듯하면 그것을 믿게 된다. 메모리 오류에서는 스택이 무고한 코드를 가리킨다.

**교훈:** 오류 종류마다 조사 전략이 다르다. 분류를 먼저 하고 도구를 고른다.

#### 관찰

**직관:** 수동 체크리스트의 세 번째 등급 — 판정 없이 사실만 적는 칸. go/no-go도 정보성도 아닌 기록이다.

**동작:** 절 구분은 **[필수 · go/no-go]**(실패 = BLOCKED) / **[정보성 · 기록만]** / **관찰**(사실만 적음)이다. 관찰 칸은 "이렇게 동작하더라"를 남기는 자리로, 나중에 정정이나 설계 변경의 근거가 된다. 예: 레거시 네트워크 바이트 규격이 `std::atomic` 없이 원시 `uint64_t`라는 관찰, 배치에서 QWidget이 뜬다는 관찰(전제를 뒤집음).

**예시:**
```
  관찰: 네트워크 바이트 규격은 std::atomic 없이 원시 uint64_t다.
  관찰: 배치에서도 QWidget 생성이 가능하다(09-07) → 머리말 전제 정정
```

**관련 코드:**
- `docs/maro-main-ui-manual-checklist.md` — 등급 구분
- `tests/maya/maroQtBatch.py:57-108` — 관찰이 뒤집은 전제

**증거:**
- §9.4, §4.3.7

**함정:** 관찰을 판정처럼 읽으면 "확인됐다"로 오해된다. 등급 표기가 그 구분을 한다.

**교훈:** 판정할 수 없는 사실도 기록할 자리를 준다. 그 기록이 나중에 전제를 뒤집는다.
