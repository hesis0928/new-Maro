#### 스펙(spec)

**직관:** 브레인스토밍으로 확정한 설계 문서. "무엇을 왜 만드는가"를 코드보다 먼저 적고, 구현은 이 문서를 근거로 삼는다.

**동작:** 경로는 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`이고 현재 26개다. 구조는 목표·데이터 모델·인터페이스·실패 모드·테스트 전략이며, 승인 뒤 플랜으로 쪼개진다. 원문이 실측으로 틀렸다고 드러나도 **지우지 않고** 정정 박스를 덧붙인다 — 이 문서들은 "최종 상태"가 아니라 "판단이 바뀐 이력"이기 때문이다. 이 프로젝트에서는 스펙·플랜이 코드와 같은 무게로 취급된다(문서 총 약 47,600줄).

**예시:**
```
docs/superpowers/specs/2026-08-13-maya-ros2-axis-node-robotization-design.md
  §3.3 "origin이 이미 …"   ← 원문 보존
  > **[정정, 2026-09-07]** 전역 컨텍스트를 쓰지 않는다.   ← 덧붙임
```

**관련 코드:**
- `docs/superpowers/specs/2026-08-13-maya-ros2-axis-node-robotization-design.md:185` — 정정 박스
- `docs/superpowers/plans/2026-08-13-maro-axis-node-slice.md` — 대응 플랜

**증거:**
- §0.1, §9.0

**함정:** 스펙을 "최신 상태 문서"로 유지하려고 원문을 고치면 왜 그 판단이 바뀌었는지가 사라진다. 이 프로젝트는 반대 방향을 택했다.

**교훈:** 설계 문서의 가치는 결론이 아니라 결론에 이른 경로다. 틀린 원문도 그 경로의 일부다.

#### 플랜(plan)

**직관:** 스펙을 태스크 단위(테스트 먼저 → 구현 → 변이 검증 → 커밋)로 쪼갠 실행 계획. 구현자가 다른 맥락 없이 그것만 보고 일할 수 있어야 한다.

**동작:** 경로는 `docs/superpowers/plans/YYYY-MM-DD-<topic>.md`이고 현재 28개다. 각 태스크는 파일 경로·인터페이스·단계별 코드·검증 명령을 담고, **모든 새 테스트에 변이 검증 스텝**(구현을 일부러 깨서 테스트가 실패하는지 확인)이 붙는다. 머리에는 Global Constraints 절이 있어 프로젝트 전체 규율을 반복한다. 플랜의 실행 기록은 `.superpowers/sdd/progress.md` 원장에 남는다(git 추적 밖).

**예시:**
```
Task 3: axisVectorForConvention
  - [ ] 실패하는 테스트 작성 → 실행해 실패 확인
  - [ ] 최소 구현 → 통과 확인
  - [ ] 변이 검증: (x,-z,y)를 (x,z,y)로 바꿔 테스트가 깨지는지 확인
  - [ ] 커밋
```

**관련 코드:**
- `docs/superpowers/plans/2026-08-13-maro-axis-node-slice.md:11` — Global Constraints
- `.superpowers/sdd/progress.md` — 실행 원장

**증거:**
- §0.1, §9.0, §11.1, §10.5, §10.6

**함정:** 플랜의 가설이 틀릴 수 있다 — `kZYX` 오일러 순서, `<axis>` 무변환 가정이 실측으로 뒤집혔다. 플랜은 지시이지 진실이 아니다.

**교훈:** 실행 계획에 검증 단계를 내장하면 계획의 오류가 구현 중에 드러난다. 변이 검증이 그 장치다.

#### 기준 커밋 `bdbe116`

**직관:** 마스터 레퍼런스의 `파일명:줄번호` 표기가 유효한 git 스냅샷. 이후 편집으로 줄 번호가 어긋날 수 있다는 단서다.

**동작:** 문서의 모든 줄 참조는 이 커밋 기준이다. 코드가 계속 바뀌므로 절대적 진실은 아니고, 읽는 사람이 `git show bdbe116:<path>`로 당시 내용을 확인할 수 있게 하는 기준점 역할을 한다. 용어 노트의 `관련 코드` 항목도 같은 이유로 줄 범위를 적되 파일 길이를 초과하지 않는지 검사한다.

**예시:**
```bash
git show bdbe116:src/maro_plugin/MaroPump.cpp | sed -n '52,84p'   # 문서가 가리킨 그 줄
```

**관련 코드:**
- `docs/maro-master-reference.md` — §0.3 표기 약속

**증거:**
- §0.3

**함정:** 기준 커밋을 적지 않은 줄 참조는 시간이 지나면 거짓이 된다. 어느 시점의 번호인지가 참조의 일부다.

**교훈:** 코드 참조에는 버전을 함께 적는다. 스냅샷 없는 줄 번호는 반감기가 짧다.

#### `.gitignore`의 `out/ build/ install/ .superpowers/ vcpkg_installed/`

**직관:** 추적하지 않는 디렉터리 목록 — 빌드 트리, SDD 진행 원장, vcpkg 설치 트리. 생성물과 로컬 상태를 저장소에서 분리한다.

**동작:** `out/`·`build/`는 CMake 산출물, `install/`은 설치 트리, `vcpkg_installed/`는 매니페스트 모드 산출물(다만 이 프로젝트는 classic 전역 트리를 쓴다), `.superpowers/`는 SDD 진행 원장이다. 원장을 추적하지 않는 것은 그것이 세션별 작업 기록이기 때문인데, 대신 `git clean -fdx`로 날아갈 수 있다는 위험이 따른다.

**예시:**
```
out/ build/ install/ .superpowers/ vcpkg_installed/
```

**관련 코드:**
- `.gitignore` — 목록
- `.superpowers/sdd/progress.md` — 추적 밖 원장

**증거:**
- §2

**함정:** 추적하지 않는 원장은 백업되지 않는다. 컨텍스트가 날아가면 `git log`로 복구해야 한다.

**교훈:** 무엇을 추적하지 않을지는 "잃어도 되는가"로 정한다. 잃으면 곤란한 것은 다른 백업을 마련한다.

#### SDD(Subagent-Driven Development)

**직관:** 태스크마다 **새 컨텍스트의 에이전트**가 구현하고, 다른 에이전트가 스펙 준수와 품질을 검토하는 개발 방식. 컨텍스트 오염 없이 계획을 실행한다.

**동작:** 흐름은 — 컨트롤러가 플랜의 태스크 N 브리프를 파일로 추출 → 구현자 에이전트(새 컨텍스트)가 TDD로 구현·커밋·보고 → 리뷰어 에이전트가 diff 패키지로 스펙 준수·품질을 판정 → Critical/Important 지적은 수정 에이전트가 처리 → 다음 태스크. 모든 태스크가 끝나면 최종 전체 브랜치 리뷰가 한 번 더 돈다. 진행 상황은 `.superpowers/sdd/progress.md`에 한 줄씩 append된다.

**예시:**
```
Task 5: complete (commits a1b2c3d..e4f5g6h, review clean)
```

**관련 코드:**
- `.superpowers/sdd/progress.md` — 진행 원장
- `docs/superpowers/plans/*.md` — 태스크 브리프 원천

**증거:**
- §9.0, §11.5

**함정:** 구현자가 플랜 외의 것을 추가하면(스코프 초과) 리뷰가 잡아야 한다. "더 좋게 만들었다"가 스펙 위반일 수 있다.

**교훈:** 새 컨텍스트로 시작하는 실행자는 계획서의 품질을 드러낸다. 계획이 부실하면 즉시 질문이 돌아온다.

#### 구현자·리뷰어

**직관:** SDD의 두 역할 — 태스크를 구현하는 에이전트와 그 결과를 검토하는 에이전트. 같은 맥락을 공유하지 않아야 검토가 의미를 갖는다.

**동작:** 구현자는 브리프 파일·인터페이스·글로벌 제약만 받고 TDD로 진행한 뒤 보고 파일에 결과를 쓴다. 리뷰어는 브리프·보고·diff 패키지 세 파일을 받아 **스펙 준수**와 **코드 품질** 두 판정을 내린다. 두 판정이 모두 통과해야 태스크가 완료된다. Critical/Important 지적은 수정 에이전트가 처리하고 재검토를 받는다.

**예시:**
```
리뷰어 출력: 스펙 ✅ / 품질 ❌ (Important: 매직 넘버 100 → 상수화)
→ 수정 에이전트 → 재검토 → 스펙 ✅ / 품질 ✅ → 태스크 완료
```

**관련 코드:**
- `.superpowers/sdd/progress.md` — 태스크별 완료 기록
- `docs/superpowers/plans/*.md` — 브리프 원천

**증거:**
- §9.0

**함정:** 컨트롤러가 리뷰어에게 "이건 지적하지 마라"고 미리 못 박으면 검토가 무력해진다. 판정은 리뷰어가 하고 조정은 그 뒤다.

**교훈:** 검토의 독립성은 맥락의 분리에서 온다. 같은 맥락을 공유한 검토는 자기 확인에 가깝다.

#### 최종 전체 브랜치 리뷰

**직관:** 모든 태스크가 끝난 뒤 브랜치 전체 diff를 한 번에 검토하는 단계. 태스크 단위로는 안 보이는 일관성 문제를 잡는다.

**동작:** 태스크별 리뷰는 그 태스크의 diff만 보므로 "파일 A의 규약과 파일 B의 규약이 어긋남" 같은 문제를 놓친다. 최종 리뷰는 `merge-base..HEAD` 전체를 보고 판정한다. 실제로 이 단계가 잡은 것들: URDF `<axis>` 재배치 누락(스펙이 틀렸음), `toPythonStringLiteral` 필요성(M3), `FILE_FLAG_FIRST_PIPE_INSTANCE`·SQOS 부재(I3), `ComUninitGuard` 선언 순서. 즉 이 단계가 이 프로젝트의 가장 중요한 결함 몇 개를 잡았다.

**예시:**
```
태스크 리뷰: 각 파일의 변경만 → 통과
최종 리뷰:  브랜치 전체 → "스펙 §3.3이 틀렸다. <axis>는 재배치가 필요하다"
```

**관련 코드:**
- `python/maroUrdfExport.py:60-87` — 최종 리뷰가 고친 축 재배치
- `src/maro_ipc/src/NamedPipe.cpp:112-140` — 최종 리뷰 I3 결과
- `src/maro_plugin/MaroPythonBridge.cpp:50-67` — 최종 리뷰 M3 결과

**증거:**
- §9.0, §7.14, §11.5

**함정:** 태스크 리뷰가 전부 통과했다고 최종 리뷰를 건너뛰면, 설계 수준의 오류가 그대로 병합된다.

**교훈:** 부분의 정합성과 전체의 정합성은 다른 검사다. 둘 다 필요하다.

#### PASS

**직관:** 수동 체크리스트 항목의 판정 어휘 중 하나 — 사람이 대화형 Maya에서 확인해 통과했다는 기록. 날짜와 실측값을 함께 적는다.

**동작:** 결과 기록 표에 Phase별로 남는다 — Phase 0-1(08-25 PASS), Phase 2(08-25 PASS), Phase 3(09-06 12개 PASS, 실측값 `[0.0,−1.0,0.0]`·Undo 큐 비오염·자기 자신 미추종), Phase 4(09-06 17개 PASS, 후속 과제 2건). PASS에 실측값을 함께 적는 것이 관례다 — "됐다"가 아니라 "이 값이 나왔다"여야 회귀 때 비교할 수 있다.

**예시:**
```
| Phase 3 | 09-06 | PASS (12개) | 실측 [0.0, -1.0, 0.0], Undo 큐 비오염 |
```

**관련 코드:**
- `docs/maro-main-ui-manual-checklist.md` — 결과 기록 표
- `docs/maro-panel-manual-checklist.md` — 패널 체크리스트

**증거:**
- §9.1, §9.4, §9.2.6
- F-214

**함정:** "PASS"만 적고 값을 안 적으면 다음 회차에 무엇과 비교할지 모른다. 판정은 데이터와 함께 남긴다.

**교훈:** 수동 검증의 결과는 숫자로 남긴다. 그래야 다음 사람이 회귀를 판단할 수 있다.

#### FAIL

**직관:** 체크리스트 항목이 실패했다는 판정. 원인 규명과 수정 날짜가 뒤따르며, 그 경위가 §14 실패 카탈로그의 씨앗이 된다.

**동작:** 대표 사례: "재시작 복원 FAIL → 원인 규명(09-10) → 수정(09-11)". 원인은 `-requiredPlugin "maro"`가 이름 로드라 `MAYA_PLUG_IN_PATH`로만 해석되는데 빌드 트리는 거기 없다는 것이었고, 해결은 `.mod` 파일 생성(`plug-ins`/`scripts`/`PATH +:=`)이었다. PATH 줄이 없으면 DLL 154개를 못 찾는다. 설치·재확인은 사용자 몫으로 남겼다.

**예시:**
```
| 재시작 복원 | 09-10 | FAIL | -requiredPlugin은 MAYA_PLUG_IN_PATH로만 해석 |
| 재시작 복원 | 09-11 | 수정 | .mod 생성(plug-ins/scripts/PATH +:=) |
```

**관련 코드:**
- `docs/maro-main-ui-manual-checklist.md` — FAIL→수정 기록
- `src/maro_plugin/CMakeLists.txt:110-130` — `.mod` 생성

**증거:**
- §9.1, §9.4
- F-023

**함정:** FAIL을 지우고 PASS로 덮어쓰면 "무엇이 왜 실패했는지"가 사라진다. 두 줄을 나란히 남긴다.

**교훈:** 실패 기록은 자산이다. 실패 카탈로그(§14)가 그 기록에서 자란다.

#### 병합

**직관:** 브랜치 작업을 main에 합치는 마지막 단계. 최종 리뷰와 수동 체크리스트를 통과한 뒤에만 한다.

**동작:** 궤도는 "브레인스토밍 → 스펙 → 플랜 → SDD 구현 → 최종 전체 브랜치 리뷰 → 수동 체크리스트 → 병합"이다. 병합 뒤에도 정정이 나올 수 있다 — LiDAR 스캔 스레드처럼 2026-08-13 스펙이 "백그라운드 격리는 타협 불가"라 했지만 병합된 실물은 메인 스레드 스캔 + 백그라운드 발행이고, 로드맵 플랜이 그 차이를 실측으로 정정했다.

**예시:**
```
스펙(08-13): "LiDAR 스캔은 백그라운드 격리 — 타협 불가"
실물(병합):  메인 스레드 스캔 + 백그라운드 발행   ← 플랜이 정정 박스로 기록
```

**관련 코드:**
- `src/maro_plugin/MaroPump.cpp:52-84` — 메인 스레드 스캔
- `src/maro_lidar/src/ScanEngine.cpp` — 스캔 엔진

**증거:**
- §9.1, §9.0, §5.2.3, §5.5.4

**함정:** 병합이 "확정"을 뜻하지 않는다. as-built가 스펙과 다르면 문서를 고치는 것이 아니라 정정 박스를 붙인다.

**교훈:** 병합은 코드의 사건이고 문서는 그 뒤를 따른다. 둘의 시차를 정정 박스가 메운다.

#### 대기

**직관:** 체크리스트·상태 표의 어휘 — 아직 확인하지 못했거나 조건이 안 맞아 판정을 미룬 항목. 실패와 구분된다.

**동작:** 예: 설정 창의 도메인 ID go/no-go는 "실측 대기"로, URDF RViz 확인은 "이 머신의 ROS 2 설치가 최소 구성이라 `rviz2` 없음 — 실행 불가"로 명시했다. 대기 항목은 커버리지가 있는 척하지 않기 위한 장치다 — 자동화되지 않은 것은 체크리스트에 go/no-go로 남기고, 확인 못 한 것은 대기로 남긴다.

**예시:**
```
| 도메인 ID 변경 | — | 대기 | os.environ 경로만 구현, 실측 미완 |
| RViz 확인      | — | 대기 | 이 머신에 rviz2 없음(최소 설치) |
```

**관련 코드:**
- `docs/maro-main-ui-manual-checklist.md` — 상태 표
- `python/maroSettingsPanel.py:165-172` — 도메인 ID 경로

**증거:**
- §9.1, §12.4, §10.10

**함정:** 대기를 오래 두면 "아무도 안 보는 항목"이 된다. 날짜와 조건(무엇이 갖춰지면 확인 가능한지)을 함께 적는다.

**교훈:** "모른다"를 표에 적을 수 있어야 정직한 상태 보고가 된다. 빈칸은 모름과 통과를 구분하지 못한다.

#### 이연

**직관:** 의도적으로 만들지 않기로 한 항목. 누락이 아니라 결정이며, 플랜의 자기 검토가 이것을 명시하도록 요구한다.

**동작:** 이연 목록의 예: `maroRobot` 노드(멤버십/publishRate/QoS), `maroAxis` 기즈모·매니퓰레이터, RViz2 시각 확인, C-2~C-4. 플랜 자기 검토 항목은 "스펙 커버리지 표, 미커버 항목(의도적 이연) 명시, 타입/이름 일관성"이며, 이연을 적지 않으면 나중에 "빠뜨린 것"과 구별되지 않는다.

**예시:**
```
  ## 스펙 커버리지
| 스펙 §  | 태스크 | 비고 |
| §4.2    | —      | 이연: 로봇 노드는 이번 슬라이스 밖 |
```

**관련 코드:**
- `docs/superpowers/plans/*.md` — 커버리지 표
- `docs/maro-master-reference.md` — §9.1 이연 목록

**증거:**
- §9.1, §9.0, §9.2.1, §9.2.5

**함정:** 이연과 누락은 결과가 같아 보인다. 문서에 적혀 있느냐가 유일한 차이다.

**교훈:** "안 만든 것"을 적는 것이 "만든 것"을 적는 것만큼 중요하다. 범위는 양쪽으로 정의된다.

#### "실행 전 스캔"에서 메운 구멍 3개

**직관:** 플랜 실행을 시작하기 전에 계획 전체를 훑어 모순·누락을 찾는 단계. Phase에서 세 구멍을 미리 메웠다.

**동작:** 메운 셋은 — 메인 스레드 펌프 부재, 런타임 시작 경로 부재, 순환 탐지 부재다. 가장 나빴던 점은 "테스트가 **틀린 이유로 통과**했을 것"이라는 것 — Manual 축이 명령을 무시한다는 검증은 런타임이 안 돌면 자동으로 참이 되기 때문이다. 실행 전 스캔은 이런 "구조적으로 무의미해지는 테스트"를 찾는 데 쓴다.

**예시:**
```
계획대로면: 런타임 시작 코드가 없음 → 발행이 아예 안 됨
그런데 테스트: "Manual 축은 명령을 무시한다" → 아무것도 안 도니까 통과
```

**관련 코드:**
- `src/maro_plugin/MaroPump.cpp:52-84` — 메워진 펌프
- `src/maro_plugin/MaroCommands.cpp:99-140` — 런타임 시작 경로
- `src/maro_plugin/MaroCommands.cpp:290-310` — 순환 탐지

**증거:**
- §9.2, §9.2.1

**함정:** 계획서의 태스크만 보면 각각은 말이 된다. 전체를 이어 봐야 "그 전제가 성립하지 않는다"가 보인다.

**교훈:** 실행 전에 계획 전체를 한 번 훑는다. 태스크 사이의 빈틈은 태스크 안에서 보이지 않는다.

#### "틀린 이유로 통과"

**직관:** 테스트가 검증하려던 이유가 아니라 우연한 다른 이유로 통과하는 상황. 이 프로젝트가 가장 경계하는 실패 유형이다.

**동작:** 사례가 여럿이다 — 런타임이 안 돌아 "명령 무시" 테스트가 자동 통과, z=0 입력이라 부호 오류를 못 잡음, 읽기가 먼저 걸려 "즉시 감지" 경로가 실행되지 않음, 수직 분할이 두 방향 모두에서 같은 결과를 내 우연히 맞음. 대응은 셋이다 — 변이 검증(일부러 깨서 실패 확인), 전제 단언(`orderingForced`), 시간/횟수 조건을 주장으로 만들기(`detectMs < 1000`).

**예시:**
```
테스트: EXPECT_FALSE(받았음)      ← 끊김 감지 실패해도 타임아웃으로 통과
개선:   EXPECT_LT(detectMs, 1000) ← "즉시"를 주장으로 고정
```

**관련 코드:**
- `tests/ipc/test_named_pipe.cpp:105-165` — 순서 강제와 시간 주장
- `tests/transform/test_convert.cpp:64-88` — 부호 축 케이스

**증거:**
- §9.2, §9.2.1, §9.2.6

**함정:** 통과하는 테스트는 아무도 의심하지 않는다. 변이 검증만이 그 의심을 제도화한다.

**교훈:** "이 테스트는 어떤 구현이면 실패하는가"를 물어야 한다. 답이 없으면 그 테스트는 아무것도 지키지 않는다.

#### 리뷰어 주목 항목

**직관:** 플랜 말미에 "리뷰어가 특히 봐야 할 곳"을 적어 두는 관례. 구현자가 자신 없는 부분을 미리 지목한다.

**동작:** 이 관례는 코드에 남지 않고 플랜 실행 기록에만 남은 아홉 교훈 중 하나다(§9.3). 나머지 여덟은 — 변이 검증의 완결 조건, 픽스처 함정 유형, 테스트 코드 삽입 위치, 좀비 mayapy(`LNK1168`), `Launch-VsDevShell.ps1` 조용한 실패, 필터링된 ctest 서브셋의 검증 공백, Maya API 헤더 실측, 정직한 공백 기록이다.

**예시:**
```
  ## 리뷰어 주목 항목
- Task 4의 eps 선택은 실측 없이 정한 값이다 — 경계 케이스 확인 요망
- Task 6의 스레드 경계는 주석으로만 보장된다
```

**관련 코드:**
- `docs/superpowers/plans/*.md` — 플랜 말미 절
- `.superpowers/sdd/progress.md` — 실행 기록

**증거:**
- §9.3

**함정:** 주목 항목을 적지 않으면 리뷰어가 diff의 크기에 비례해 주의를 분산한다. 작은 줄이 가장 위험할 수 있다.

**교훈:** 검토를 받는 쪽이 위험 지점을 지목하면 검토의 밀도가 올라간다. 자신 없음을 적는 것이 프로세스의 일부다.

#### 정직한 공백

**직관:** "검증하지 못한 것"을 그대로 적는 관례. 커버리지가 있는 척하지 않는 것이 이 프로젝트의 규율이다.

**동작:** 예 — 필터링된 ctest 서브셋으로 돌렸을 때 "이 실행은 전체가 아니다"를 기록, RViz 확인은 "이 머신에 rviz2 없음"으로 실행 불가를 명시, 배치에서 검증 불가능한 항목은 수동 체크리스트로 넘기되 go/no-go 등급을 붙인다. 각 테스트 스크립트의 독스트링도 "이 파일이 못 하는 것"을 먼저 못 박는다.

**예시:**
```python
"""브리지 펌프 통합 테스트.

이 파일이 못 하는 것: 실제 뷰포트 렌더, Qt 위젯 포커스, 사용자 상호작용.
그것들은 docs/maro-main-ui-manual-checklist.md로 넘긴다.
"""
```

**관련 코드:**
- `tests/maya/test_bridge_pump.py:1-20` — 독스트링 관례
- `docs/maro-main-ui-manual-checklist.md` — 넘겨받는 쪽

**증거:**
- §9.3, §8.0, §10.10

**함정:** 공백을 적지 않으면 나중에 "테스트가 있는데 왜 못 잡았나"라는 잘못된 질문이 나온다. 범위를 미리 적으면 그 질문이 안 생긴다.

**교훈:** 테스트의 가치는 커버리지 숫자가 아니라 "무엇을 지키는지"가 분명한 데서 온다. 공백도 그 선언의 일부다.

#### 체크리스트(manual checklist)

**직관:** 배치 mayapy가 원리적으로 검증할 수 없는 항목(뷰포트 렌더·Qt 도킹·핫키·언로드)을 사람이 대화형 Maya에서 확인하는 문서. 두 개가 있다.

**동작:** `docs/maro-main-ui-manual-checklist.md`와 `docs/maro-panel-manual-checklist.md`. 항목마다 절차·기대 결과·판정(PASS/FAIL/대기)과 등급([필수 · go/no-go] / [정보성 · 기록만] / 관찰)이 붙는다. 자동 테스트가 "못 하는 것"을 명시적으로 넘겨받는 문서라, 자동화 커버리지의 빈틈이 여기에 드러난다.

**예시:**
```
  ### §6-1 포인트클라우드 [필수 · go/no-go]
1. createNode maroPointCloud
2. 뷰포트에 점이 보이는가
   → 09-06 FAIL(크래시) / 09-07 PASS
```

**관련 코드:**
- `docs/maro-main-ui-manual-checklist.md` — 메인 UI
- `docs/maro-panel-manual-checklist.md` — 패널

**증거:**
- §0.1, §8.0, §10.4, §10.10

**함정:** 수동 항목은 실행 비용이 높아 미뤄진다. 필수와 정보성을 등급으로 나눠 최소한 필수만은 돌게 한다.

**교훈:** 자동화의 경계를 문서로 만들면 그 경계가 관리 대상이 된다. 경계가 흐리면 아무도 확인하지 않는다.

#### go/no-go 스파이크

**직관:** "이게 가능한가"만 판정하는 최소 구현. 본 구현 전에 위험을 제거하는 실험이다.

**동작:** Phase 0-1의 스파이크는 "창을 띄운 채 `unloadPlugin`해도 Maya가 안 죽는가"를 판정했다. 내용은 네이티브 `workspaceControl` + `formLayout` 안에 `cmds.modelPanel()` 뷰포트와 `MQtUtil::addWidgetToMayaLayout`로 끼운 PySide6 위젯이 공존하는 스무 줄이다. 그 스무 줄에도 함정이 셋 있었다 — `MFnPlugin.h` 중복 포함(LNK2005), Python 리터럴 이스케이프, `asChar()` 로케일 문제.

**예시:**
```
go/no-go: 창을 띄운 채 unloadPlugin → Maya가 살아 있는가?
→ 살아 있음 → 본 구현 진행
```

**관련 코드:**
- `python/maroMainWindow.py:73-100` — 스파이크가 커진 본체
- `src/maro_plugin/MaroPythonBridge.cpp:50-67` — 스파이크에서 발견한 이스케이프 문제

**증거:**
- §6.9, §6.9.2, §11.1

**함정:** 스파이크 코드가 그대로 본 구현이 되면 "판정용 최소"의 허술함이 남는다. 스파이크의 발견을 본 구현에 옮기되 코드는 다시 쓴다.

**교훈:** 가장 위험한 가정을 가장 싸게 검증하는 실험을 먼저 한다. 그 실험이 함정 목록도 준다.

#### 수동 체크리스트

**직관:** 배치가 못 보는 것(도킹·포커스·핫키·실제 렌더)을 사람이 검증하는 절차서. 자동 테스트의 독스트링이 넘긴 항목을 받는다.

**동작:** 각 테스트 스크립트가 "이 파일이 못 하는 것"을 독스트링에 먼저 못 박고, 그 항목들이 체크리스트로 모인다. 다만 "배치라서 불가능"은 세 번 실측으로 뒤집혔다 — QWidget(`maroQtBatch`), Viewport 2.0(`ogsRender`), ASan(선로드). 그래서 항목을 넘기기 전에 "정말 배치에서 불가능한가"를 한 번 더 묻는 규율이 생겼다. 다만 `cmds` UI는 배치에서 정말 꺼져 있다.

**예시:**
```
자동: test_point_cloud_draw.py — 드로우 오버라이드 호출 여부
수동: 뷰포트에 실제로 점이 보이는가, 카메라를 돌려도 유지되는가
```

**관련 코드:**
- `tests/maya/maroQtBatch.py:57-108` — 뒤집힌 전제 1
- `docs/maro-main-ui-manual-checklist.md` — 수동 항목

**증거:**
- §8.0, §1.3, §7.3, §11.1

**함정:** "수동으로 넘긴다"가 "검증하지 않는다"가 되기 쉽다. 등급(go/no-go)과 날짜를 붙여야 실제로 돈다.

**교훈:** 자동/수동의 경계는 고정된 것이 아니라 실측으로 움직인다. 주기적으로 다시 묻는다.

#### "이 파일이 못 하는 것" 독스트링 관례

**직관:** 각 테스트 스크립트가 자기 검증 범위의 **한계**를 첫머리에 선언하는 관례. 커버리지 착시를 막는다.

**동작:** 독스트링이 "이 파일이 못 하는 것"을 먼저 적고, 그 항목들을 수동 체크리스트로 넘긴다. 예: 배치 테스트는 실제 뷰포트 픽셀을 못 보고, 파이프 테스트는 실제 Maya 크래시를 못 만들고, 순수 함수 테스트는 Maya 씬 상태를 못 본다. 읽는 사람이 "이 테스트가 통과하면 무엇이 보장되는가"를 즉시 알 수 있다.

**예시:**
```python
"""LiDAR 발행 통합 테스트.

이 파일이 못 하는 것:
- 실제 뷰포트에 포인트가 그려지는지 (수동 체크리스트 §6-1)
- RViz에서의 시각 확인 (이 머신에 rviz2 없음)
"""
```

**관련 코드:**
- `tests/maya/test_publish.py:1-20` — 관례 적용
- `tests/maya/test_bridge_pump.py:1-20` — 같은 관례

**증거:**
- §8.0

**함정:** 한계를 적지 않으면 "테스트가 있다"가 "검증됐다"로 읽힌다. 그 착각이 회귀를 늦게 발견하게 만든다.

**교훈:** 테스트는 자기 범위를 스스로 문서화해야 한다. 범위 선언이 곧 다음 테스트의 목록이다.

#### 정정 박스(`> **[정정, 날짜 · 출처]**`)

**직관:** 스펙·플랜의 원문이 틀렸을 때 원문을 남기고 그 아래에 붙이는 인용 블록. 네 가지를 적는다 — 무엇이, 왜 틀렸고, 어떻게 고쳤고, **왜 기존 테스트가 못 잡았는지**.

**동작:** 마지막 항목이 이 관례의 핵심이다 — 틀린 것을 고치는 것보다 "왜 못 잡았는지"가 다음 테스트 설계를 바꾼다. 실제 정정 예: 전역 rclcpp 컨텍스트 금지(09-07), `aSourceValue` 타입(08-25 최종 리뷰), `kZYX` 오일러 가설 반증, 배치 QWidget 불가 철회. 문서는 "최종 상태"가 아니라 "판단이 바뀐 이력"이라는 선언이다.

**예시:**
```markdown
> **[정정, 2026-09-07 · MaroRosContext 최종 리뷰]** 전역 컨텍스트를 쓰지 않는다.
> 무엇: §4.2의 rclcpp::init 사용. 왜 틀렸나: Maya는 플러그인 다중 프로세스…
> 어떻게: Context를 직접 만들어 NodeOptions로 전달. 왜 못 잡았나: 단일 플러그인 테스트뿐
```

**관련 코드:**
- `docs/superpowers/specs/2026-08-13-maya-ros2-axis-node-robotization-design.md:185` — 실제 정정 박스
- `docs/superpowers/specs/2026-08-25-maro-main-ui-phase4-axis-capability-editor-design.md:41` — 타입 정정

**증거:**
- §9.0, §9.4
- F-252

**함정:** 정정 박스가 쌓이면 원문과 최신 판단이 섞여 읽기 어려워진다. 그래서 as-built 요약(§13 해설지)이 따로 필요하다.

**교훈:** 이력 보존과 최신 상태 제공은 다른 문서의 일이다. 하나로 둘 다 하려 하면 둘 다 나빠진다.

#### Global Constraints

**직관:** 플랜 머리에 두는, 프로젝트 전체에 적용되는 규율 목록. 모든 태스크의 요구사항에 암묵적으로 포함된다.

**동작:** 초기(2026-08-13)에는 스레드 경계·예외 경계·NaN·compute 불변·두 가지 쓰기 경로·조용한 실패 금지·C++17이었고, 이후 누적됐다 — UTF-8 소스, 해시 불변성, book 격리, `--config Release` 명시 등. `--config Release`가 들어간 이유는 컨피그를 안 주면 Debug로 링크하다 `LNK2038`(`_ITERATOR_DEBUG_LEVEL` 불일치)이 나기 때문이다(F-002). 즉 이 절은 사고의 누적 기록이다.

**예시:**
```markdown
  ## Global Constraints
- Maya API 호출은 메인 스레드에서만
- 모든 콜백 경계에서 예외를 잡되 기록한다(조용한 실패 금지)
- 빌드·테스트 명령에는 항상 `--config Release`
```

**관련 코드:**
- `docs/superpowers/plans/2026-08-13-maro-axis-node-slice.md:11` — 초기 목록
- `docs/superpowers/plans/2026-08-14-maro-diag-foundation.md:13` — 누적된 목록

**증거:**
- §9.0, §9.2.2
- F-002

**함정:** 목록이 길어지면 아무도 안 읽는다. 각 항목이 실제 사고에서 왔다는 점을 한 줄로 붙이면 읽힌다.

**교훈:** 규율은 사고의 기록에서 자란다. "왜 이 규칙이 있는가"를 함께 적으면 규칙이 살아 있다.

#### 실측 vs 추론

**직관:** 관측한 사실과 그로부터 유도한 가설을 **문장 단위로** 구분해 표기하는 관례. 같은 문단에 섞이면 가설이 사실처럼 읽힌다.

**동작:** 예: 재시작 복원 실패 분석에 "이쪽은 추론이고 실측이 아니다"라는 문장이 그대로 들어간다. 이 관례 덕에 나중에 "어디부터 확인해야 하는가"가 분명해진다 — 추론으로 표시된 부분이 먼저 검증 대상이다. 마스터 레퍼런스도 같은 규칙을 이어받아 "실측(날짜)"과 "추론"을 나눠 적는다.

**예시:**
```
실측: overscan=1.0과 2.0의 depth AOV가 픽셀 단위로 동일했다.
추론: 따라서 overscan은 뷰포트 표시 전용일 것이다. (문서로 확인됨)
```

**관련 코드:**
- `python/maroSyntheticDataPointCloud.py:33-45` — 실측/추론 구분 주석
- `docs/maro-master-reference.md` — 같은 표기

**증거:**
- §9.0

**함정:** 추론이 반복 인용되면 어느새 사실로 굳는다. 표기가 없으면 출처를 되짚을 수 없다.

**교훈:** 문장마다 근거 등급을 붙이는 비용은 작고, 잘못된 전제를 되짚는 비용은 크다.

#### 자기 검토(self-review) 항목

**직관:** 스펙·플랜을 쓴 직후 자기 문서를 훑는 체크리스트. 리뷰어에게 가기 전에 스스로 거르는 단계다.

**동작:** 스펙 자기 검토는 — 플레이스홀더(TBD·TODO), 내부 모순, 스코프(단일 구현 계획으로 충분한가), 모호성(두 가지로 읽히는 요구사항). 플랜 자기 검토는 — 스펙 커버리지 표, 미커버 항목(의도적 이연) 명시, 타입/이름 일관성(태스크 3에서 쓴 함수 이름이 태스크 7에서 다른 이름으로 바뀌지 않았는가).

**예시:**
```
스펙 자기 검토: TBD 0건 / 모순 0건 / 스코프 OK / 모호 1건 → 수정
플랜 자기 검토: 커버리지 §1~§7 전부 / 이연 §4.2 명시 / 이름 일관성 OK
```

**관련 코드:**
- `docs/superpowers/specs/*.md` — 자기 검토를 거친 문서들
- `docs/superpowers/plans/*.md` — 커버리지 표

**증거:**
- §9.0

**함정:** 자기 검토를 형식적으로 하면 "체크만 하고 안 고침"이 된다. 항목마다 발견 건수를 적으면 실제로 훑게 된다.

**교훈:** 남에게 보내기 전의 한 번이 가장 싸다. 자기 검토 항목을 고정하면 매번 같은 품질이 나온다.

#### as-built

**직관:** 구현 후의 실제 상태. 코드가 최신이고 문서가 그것을 따라가는 관계를 뜻한다.

**동작:** 스펙이 설계 의도라면 as-built는 병합된 실물이다. 둘이 다르면 문서를 덮어쓰는 것이 아니라 정정 박스로 차이를 기록한다. 마스터 레퍼런스(§13 해설지)는 as-built 관점의 문서 — "지금 코드가 이렇게 되어 있고 왜 그런가"를 적는다. 그래서 스펙·플랜(이력)과 마스터(현재)가 역할을 나눈다.

**예시:**
```
스펙:   LiDAR 스캔은 백그라운드 스레드 (타협 불가)
as-built: 메인 스레드 스캔 + 백그라운드 발행
정정 박스: 왜 바뀌었는지, 왜 테스트가 못 잡았는지
```

**관련 코드:**
- `docs/maro-master-reference.md` — as-built 해설
- `src/maro_plugin/MaroPump.cpp:52-84` — 실제 스캔 위치

**증거:**
- §9.0

**함정:** as-built 문서가 없으면 새 사람이 스펙을 현재 상태로 오해한다. 스펙만 읽고 코드를 고치면 방향이 어긋난다.

**교훈:** "의도"와 "현재"를 다른 문서로 둔다. 둘 사이의 차이를 기록하는 것이 셋째 문서의 일이다.

#### go/no-go

**직관:** 수동 체크리스트 항목의 등급 중 가장 강한 것 — 실패하면 BLOCKED다. 통과하지 않으면 다음 단계로 못 간다.

**동작:** 절 구분은 **[필수 · go/no-go]**(실패 = BLOCKED) / **[정보성 · 기록만]** / **관찰**(사실만 적음) 셋이다. 남은 미확인 필수 항목 목록이 문서에 명시돼 있다 — §6-1 재확인(5), §6-2(6), §6-3(5), §7 스켈레톤(8), 진단 패널 임베드(5), 설정 창 도메인 ID, URDF RViz 확인(rviz2 없음으로 실행 불가). Arnold 절은 go/no-go 두 개가 이미 배치 렌더로 실측 확정돼 회귀 확인용으로만 남았다.

**예시:**
```
  ### §7 스켈레톤 업로드 [필수 · go/no-go]   ← 실패하면 BLOCKED
  ### §8 성능 관찰 [정보성 · 기록만]          ← 수치만 남김
```

**관련 코드:**
- `docs/maro-main-ui-manual-checklist.md` — 등급 구분과 미확인 목록
- `python/maroSkeletonUpload.py:41-88` — §7 대상 기능

**증거:**
- §9.4, §11.1, §10.10, §6.9.2
- F-254, F-288

**함정:** 모든 항목을 필수로 만들면 아무것도 못 넘어간다. 등급을 나누는 판단 자체가 설계다.

**교훈:** 검증 항목에 등급을 매기면 "지금 무엇이 막고 있는가"가 한눈에 보인다.

#### BLOCKED

**직관:** go/no-go 항목이 실패했을 때의 상태. 다음 단계(병합·배포)로 진행할 수 없다는 뜻이다.

**동작:** BLOCKED는 "고쳐야 넘어간다"를 뜻하므로 원인 규명과 수정이 뒤따른다. 09-06 포인트클라우드 CRITICAL FAIL이 그 예 — `createNode` 단독으로 크래시해 BLOCKED였고, 09-07에 `MFnPointArrayData::array()` 댕글링을 고쳐 해제됐다. 정보성 항목의 실패는 BLOCKED가 아니라 기록으로만 남는다.

**예시:**
```
§6-1 [필수 · go/no-go] → 09-06 FAIL → BLOCKED
→ 09-07 원인 규명·수정 → PASS → 해제
```

**관련 코드:**
- `docs/maro-main-ui-manual-checklist.md` — 상태 기록
- `src/maro_plugin/MaroPointCloudNode.cpp:241-390` — 해제시킨 수정

**증거:**
- §9.4, §11.1

**함정:** BLOCKED를 오래 두면 우회 경로가 생기고 체크리스트가 무시된다. 해제 조건을 명확히 적는다.

**교훈:** 차단 상태는 명시적으로 선언하고 해제도 명시적으로 기록한다. 암묵적 진행이 가장 위험하다.

#### 정보성

**직관:** 체크리스트 등급 중 "기록만 한다"는 단계. 실패해도 진행을 막지 않지만 수치는 남긴다.

**동작:** 성능 관찰·부가 기능 확인처럼 판정보다 데이터가 중요한 항목에 붙인다. 등급이 셋으로 나뉘는 덕에 필수 항목의 신호가 흐려지지 않는다 — 모든 것이 필수면 필수의 의미가 없다. 세 번째 등급인 **관찰**은 판정 없이 사실만 적는 칸이다.

**예시:**
```
  ### §8 스캔 성능 [정보성 · 기록만]
- 5000 레이 스캔 소요: 12ms (09-06 측정)
```

**관련 코드:**
- `docs/maro-main-ui-manual-checklist.md` — 등급별 절
- `docs/maro-panel-manual-checklist.md` — 패널 쪽 관찰 항목

**증거:**
- §9.4

**함정:** 정보성 항목의 수치를 안 적으면 등급의 의미가 사라진다. 판정이 없을수록 데이터가 중요하다.

**교훈:** 모든 확인이 합격/불합격일 필요는 없다. 관측만으로 가치가 있는 항목을 따로 둔다.
